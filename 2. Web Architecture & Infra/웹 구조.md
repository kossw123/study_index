## 왜 필요한가?

- 현대에 와서는 동적 웹 프로그래밍 구조도 여러 형태로 발전했다.
- 하드웨어 진화에 따라 할 수 있는 범위가 넓어졌기 때문에, 구조도 진화했다.

## 정의

# # 1. 모놀리식 아키텍처 (Monolithic Architecture)

> WAS 갯수: 1
> DB 갯수: 1
   추천 상황: 초기 스타트업, 단순한 서비스

- **핵심 개념:** 
	- 소프트웨어의 모든 비즈니스 로직을 **단일 배포 단위(Single Deployment Unit)**로 묶어 하나의 실행 파일로 빌드하고 배포하는 전통적인 방식. 
- **인프라 확장:** 
	- "WAS 1대"에 국한되지 않으며, 트래픽 증가 시 동일한 모놀리식 애플리케이션 인스턴스를 여러 대(Scale-out)로 확장하고 로드밸런서와 DB 복제본을 연결하여 운영할 수 있다.
- **장점:** 
	- 배포 파이프라인이 단순하고, 컴포넌트 간 통신 비용이 없으며, 초기 개발 속도가 매우 빠르다. 
- **단점:** 
	- 코드베이스가 거대해지면 빌드/배포 시간이 길어지고, 작은 수정 사항 때문에 전체 시스템을 다시 배포해야 한다. 
	- 또한 특정 영역의 메모리 누수가 전체 시스템의 다운으로 이어질 수 있다.


소프트웨어의 모든 기능을 하나의 단일 프로젝트로 개발, 하나의 실행파일로 빌드해서 배포하는 전통적인 방법이다.
그래서 기능도 하나의 폴더로 구성되는 경우가 많다.

기본적으로 동적 웹 프로그래밍 구조를 모놀리식이라고 부른다.
그런데 왜 굳이 서로 다른 것처럼 얘기할까?란 질문에 다음과 같이 답변할 수 있겠다.

동적 웹 프로그래밍이라는 개념에서의 구조와 모놀리식 구조는 서로 바라보는 관점이 다르다.
동적 웹 프로그래밍은 서로 통신을 주고받는 결과에 대한 이야기라면, 모놀리식은 인프라에 어떻게 배치할 것인가에 대한 이야기다.

“모놀리식의 가장 중요한 이념은 주소가 하나고, 로직이 하나고, 저장소가 하나다 라는 것이다.”

이런 개념은 하나의 파이프라인만 잘 관리하면 개발과 유지보수가 편하다는 장점이 있다.
또한 단점도 파이프라인이 하나라서 하나라도 잘못된다면 모든 기능이 정지된다.


# 2. 모듈러 모놀리스 (Modular Monolith)

>WAS 갯수: 1
>DB 갯수: 1(또는 스키마 분리)
>추천 상황: 코드 복잡도를 낮추고 싶은 중소규모 서비스

- **핵심 개념:** 
	- 배포와 인프라는 모놀리식처럼 '단일 단위'로 가져가되, **소스코드 수준에서 비즈니스 도메인 간의 경계와 의존성을 엄격히 격리(Encapsulation)**하는 구조. 
- **구현 방식:** 
	- 단순한 '폴더 분리'를 넘어, 빌드 도구(예: Java Gradle Multi-module, NestJS Module 등)를 이용해 모듈 간의 참조를 컴파일 단계에서 강제하고 제한한다. 
	- 모듈 간 통신은 네트워크(HTTP)가 아닌 메모리 상의 내부 호출 인터페이스를 통해 안전하게 이루어진다. 
- **장점:** 
	- 분산 인프라 구축 비용 없이 모놀리식의 단순한 배포 장점을 유지한다. 
	- 도메인 간 경계가 명확하여 향후 특정 모듈만 마이크로서비스(MSA)로 추출할 때 유리하다. 
	- 단일 DB 안에서 트랜잭션 무결성(ACID)을 쉽게 보장할 수 있다. 
- **단점:** 여전히 하나의 언어/프레임워크 스택에 종속되며, 배포 단위가 하나이므로 전체 다시 빌드/배포해야 하는 모놀리식의 물리적 한계는 공유한다.


모놀리식의 한계인 하나의 파이프라인 때문에 장애가 생기면 발생하는 문제를 해결하기 위해 다음과 같이 구성한다.

1. 배포와 인프라, 즉 단일 프로젝트로 개발하고 하나의 실행파일로 배포한다.
2. 그러나 단일 프로젝트에 포함되어야 할 기능들은 단일 프로젝트에서 여러 폴더로 계층을 만들어서 구현한다.

모놀리식의 장점은 가져오면서 소스코드 구성은 보기 쉽게 기능별로 계층을 나눠서 구혆한다는 뜻이다.

장점을 보면, 모놀리식과 동일한 구조를 가지고 있다.

```
클라이언트 <-> 웹 서버 <-> WAS <-> DB
```

1. 그래서 따로 복잡한 분산 인프라 기술이 필요없기 때문에 진입장벽이 낮다.
2. 모듈간 통신이 HTTP가 아닌 메모리 연산으로 이뤄져 처리속도가 매우 빠르기도 하다.
3. 계층을 잘 구성하면 트랜잭션의 무결성을 보장할 수 있다.
4. MSA로 전환하기도 쉽다. 이미 소스코드는 기능별로 분산화 되어있기 떄문에 이식만 하면 된다.


그러나 한계도 명확하다. 

1. 모놀리식을 골자로 삼아서 기술 스택이 하나의 프로그래밍 언어로 되어있다.
2. 코드는 격리되었으나, 배포 단위가 하나라서 고칠 때마다 다시 빌드하고 배포해야 한다.
3. 특정 모듈에서 메모리 누수가 발생한다면 전체가 죽는다.



# 3. 마이크로서비스 아키텍처 (MSA)

>WAS 갯수: 수십 ~ 수백 개
>DB 갯수: 서비스 당 하나씩
>추천 상황: 대기업, 대규모 트래픽, 거대한 개발 팀

- **핵심 개념:** 
	- 비즈니스 도메인 경계(Bounded Context)를 기준으로 **소프트웨어를 완전히 독립적인 작은 서비스들로 쪼개고, DB까지 서비스별로 격리**하는 분산 아키텍처 스타일. 
- **인프라 구조:** 
	- 각 서비스는 완전히 독립된 프로세스와 인프라를 가지며, 상호 간에는 네트워크 통신(REST API, gRPC)이나 이벤트 메시징(Kafka 등)을 통해 협력한다. 
- **장점:** 
	- 팀별 독립적인 배포가 가능하고, 서비스별로 가장 적합한 기술 스택(Polyglot)을 선택할 수 있으며, 트래픽이 몰리는 특정 서비스만 정밀하게 확장(Scale-out)할 수 있다. 
- **단점 및 주의점:** 
	- **장애 전파 위험:** 
		- 서비스들이 엮여있을 때, 한 서비스의 장애가 전체로 번질 수 있다. 이를 기 위해 서킷 브레이커(Circuit Breaker)나 비동기 이벤트 기반 통신(EDA) 같은 추가적인 복잡한 장치가 필수적이다. 
	- **분산 데이터 관리의 어려움:** 
		- DB가 쪼개지므로 기존 RDB의 조인(Join)이나 단일 트랜잭션을 쓸 수 없어, 사가(Saga) 패턴이나 결과적 일관성(Eventual Consistency)을 직접 구현해야 하므로 전환/구축 난이도가 매우 높다.

```
클라이언트 <-> 웹 서버 <-> WAS  <-> DB
                     <-> WAS <->
                     <-> WAS <->
                     <-> WAS <->
```

이런식으로 확장해 나가는 구조를 마이크로서비스 아키텍처라 부른다.
WAS만 확장하는게 아닌 DB도 확장하여 구현할 수 있다.
이 구조의 특징은 각 WAS마다 담당하는 기능이 있다는 것이다.

각 WAS가 담당하는 기능에 장애가 생겨도 다른 기능은 멀쩡히 살아있다.
또한 각 기능마다 언어 스택이 달라도 상관없이 돌아간다.
그리고 특정 부분에 트래픽이 몰리면 필요한 부분만 서버를 늘릴 수 있다.


# 4. 서버리스 (Serverless / FaaS)

>WAS 갯수: 없음(클라우드 시스템 활용)
>DB 갯수: 필요한 만큼 연동
>추천 상황: 이벤트성 작업, 백그라운드 처리, 배치 작업

- **핵심 개념:** 
	- 개발자가 서버의 프로비저닝, 관리, 스케일링 등 **인프라 운영 부담을 전혀 신경 쓰지 않고, 비즈니스 코드(함수 단위)만 클라우드에 올려 실행**하는 인프라 운영 모델. 
- **구정 방식:** 
	- MSA가 설계 방식이라면 서버리스는 배포/운영의 형태다. 
	- (즉, 모놀리스를 서버리스 환경에 띄울 수도 있고, MSA의 특정 컴포넌트를 서버리스 함수로 만들 수도 있다.) 
	- 요청이 올 때만 인프라가 임시로 구동(Cold Start)되고 처리가 끝나면 소멸하므로 가동 시간에 대해서만 비용을 지불한다.
- **추천 상황:** 
	- 상시 구동이 필요 없는 이벤트성 작업, 주기적인 배치 작업, 백그라운드 이미지/동영상 프로세싱 등에 최적화되어 있다.

이름 그대로 서버가 항상 켜질 필요가 없이, 요청이 들어오면 
“새 컴퓨터를 만들고 요청이 끝나면 폐기”하는 방식으로 동작한다.

기본적으로 MSA와 같은 구조를 띄지만, 별도의 WAS가 없다.
그러므로 이 부분은 AWS, Oracle과 같이 대기업의 클라우드 시스템을 이용해 매꾼다.

그러면 최종적으로 정리해보자.

1. 서버리스는 MSA의 핵심사상을 이어받아 기능을 함수 단위(FaaS)로 쪼갠 구조를 가진다.
2. 그러나 로드밸런서는 있지만, 업스트림을 대상으로 할 WAS가 없다.
    1. 이 부분은 AWS, Oracle과 같은 클라우드 시스템이 대신한다.
3. DB는 따로 연결한다.

## 프로젝트에서는 어디에서 사용하는가?
