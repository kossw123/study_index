## 왜 필요한가?

### ① 마이크로서비스(MSA)와 컨테이너 환경의 등장

- 과거 단일 서버(Monolithic) 시절에는 서버 한 두 곳에 들어가 `tail -f app.log`를 치면 장애를 잡을 수 있었습니다. 
- 하지만 현재는 수십~수백 개의 Docker 컨테이너가 복잡하게 통신하므로, **특정 에러 하나가 어디서 터졌는지 일일이 찾아다니는 것이 불가능**해졌습니다.

### ② "도구 파편화" 문제 해결

- 기존에는 메트릭은 Prometheus, 로그는 ELK 스택(Elasticsearch), 트레이스는 Jaeger로 따로따로 보느라 브라우저 탭을 여러 개 띄우고 시간대를 대조해야 했습니다. 

> LGTM은 **Grafana라는 단일 UI 안에서 이 세 가지를 매끄럽게 연결**해 줍니다.

### ③ 압도적인 비용 및 리소스 효율성

- **Loki**는 전체 로그 본문을 인덱싱하는 대신 타임스탬프와 라벨(Label)만 인덱싱하고 로그 텍스트는 압축하여 저장한다.
- **Tempo**는 복잡한 인덱스 데이터베이스를 유지하는 대신, **분산 트레이스 데이터(Span)를 거대한 블록(Block) 형태로 묶어 오브젝트 스토리지(S3 등)에 직접 저장**한다.
- 두 도구 모두 무거운 인덱스 서버를 두지 않기 때문에, 기존 ELK 스택 대비 **데이터 저장 비용과 메모리 리소스를 획득하는 데 매우 효율적**이다.

## 정의

Grafana Labs에서 주도하는 오픈소스 모니터링 스택으로, 시스템 관찰 가능성의 3대 요소인 Metrics(메트릭), Logs(로그), Traces(트레이스)를 하나로 통합한 조합입니다.

| **영문** | **오픈소스 이름**                   | **담당 역할**               | **비유**                            |
| ------ | ----------------------------- | ----------------------- | --------------------------------- |
| **L**  | **Loki**                      | **Logs (로그)**           | 시스템의 상세 일기장 (에러 내용, 파라미터 등)       |
| **G**  | **Grafana**                   | **Visualization (시각화)** | 로그·메트릭·트레이스를 한 화면에 보여주는 관제탑       |
| **T**  | **Tempo**                     | **Traces (트레이스)**       | 요청이 여러 서비스를 거쳐가는 여정 지도 (병목 지점 추적) |
| **M**  | **Prometheus** (또는 **Mimir**) | **Metrics (메트릭)**       | 시스템의 대시보드 계기판 (CPU, 메모리, TPS 등)   |
## 동작 과정

LGTM의 진가는 세 가지 데이터를 연관(Correlation)지어 탐정처럼 장애를 추적할 때 나타난다.
- 단, 이를 위해서는 애플리케이션에 OpenTelemetry 등을 통한 Trace ID 주입(계측)과 Grafana 데이터 소스의 파생 필드(Derived Fields) 연동 설정이 선행되어야 합니다.

```
[메트릭 이상 감지] ➔ [트레이스 병목 추적] ➔ [로그 원인 파악]
```

1. **1단계 (Metrics):** 
	- Grafana 대시보드에서 `Prometheus/Mimir`를 통해 API 응답 시간이 튀거나 에러율이 급증하는 것을 감지합니다.
2. **2단계 (Traces):** 
	- 해당 시점의 지연된 요청을 `Tempo`에서 조회하여 어떤 서비스 구간(A ➔ B ➔ DB)에서 병목이 생겼는지 지도를 확인합니다.
3. **3단계 (Logs):** 
	- **로그에 찍힌 동일한 `Trace ID` 식별자를 매핑**하여 `Loki`로 바로 이동한 뒤, 그 순간 구체적으로 어떤 예외(Exception) 에러 메시지가 남았는지 확인합니다.


## 어떤 상황에서 사용하면 좋을까?

- **MSA 구조에서 구간별 병목을 시각화하고 싶을 때:** 
	- 여러 API 간의 호출 관계와 구간별 소요 시간을 한눈에 보여줍니다.
- **인프라 유지 비용(인프라 리소스)을 아끼고 싶을 때:** 대용량 로그/트레이스 데이터를 고가의 DB 대신 저렴한 S3/오브젝트 스토리지에 저장하여 운영 비용을 절감할 수 있습니다.

## 도입 전 현실적인 유의사항

- **초기 학습 및 빌드 공수:** 애플리케이션 전반에 분산 트레이싱을 전파하고 인프라 설정을 맞추는 과정은 소규모 팀에게 **적지 않은 기술적 부채와 인건비(공수)**를 요구할 수 있습니다.
- **해결 시간이 아닌 '분석 효율'의 향상:** 도구가 단일화되어 장애 원인 추적 경로가 단축되지만, 로그 해석 능력과 인프라 숙련도에 따라 실제 원인 파악 시간은 상이할 수 있습니다.
