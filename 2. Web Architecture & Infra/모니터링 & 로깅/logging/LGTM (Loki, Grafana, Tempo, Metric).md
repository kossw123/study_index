## 왜 필요한가?

### ① 마이크로서비스(MSA)와 컨테이너 환경의 등장

- 과거 단일 서버(Monolithic) 시절에는 서버 한 두 곳에 들어가 `tail -f app.log`를 치면 장애를 잡을 수 있었습니다. 
- 하지만 현재는 수십~수백 개의 Docker 컨테이너가 복잡하게 통신하므로, **특정 에러 하나가 어디서 터졌는지 일일이 찾아다니는 것이 불가능**해졌습니다.

### ② "도구 파편화" 문제 해결

- 기존에는 메트릭은 Prometheus, 로그는 ELK 스택(Elasticsearch), 트레이스는 Jaeger로 따로따로 보느라 브라우저 탭을 여러 개 띄우고 시간대를 대조해야 했습니다. 

> LGTM은 **Grafana라는 단일 UI 안에서 이 세 가지를 매끄럽게 연결**해 줍니다.

### ③ 압도적인 비용 및 리소스 효율성

- 특히 **Loki**와 **Tempo**는 전체 데이터를 인덱싱하는 대신 텍스트 자체만 효율적으로 압축하여 오브젝트 스토리지(S3 등)에 저장하기 때문에, 기존 ELK 스택 대비 **서버 리소스(RAM/CPU)와 저장 비용을 대폭 절감**할 수 있습니다.

## 정의

Grafana Labs에서 주도하는 오픈소스 모니터링 스택으로, 시스템 관찰 가능성의 3대 요소인 Metrics(메트릭), Logs(로그), Traces(트레이스)를 하나로 통합한 조합입니다.

| **영문** | **오픈소스 이름**               | **담당 역할**               | **비유**                            |
| ------ | ------------------------- | ----------------------- | --------------------------------- |
| **L**  | **Loki**                  | **Logs (로그)**           | 시스템의 상세 일기장 (에러 내용, 파라미터 등)       |
| **G**  | **Grafana**               | **Visualization (시각화)** | 로그·메트릭·트레이스를 한 화면에 보여주는 관제탑       |
| **T**  | **Tempo**                 | **Traces (트레이스)**       | 요청이 여러 서비스를 거쳐가는 여정 지도 (병목 지점 추적) |
| **M**  | **Mimir** (또는 Prometheus) | **Metrics (메트릭)**       | 시스템의 대시보드 계기판 (CPU, 메모리, TPS 등)   |

## 동작 과정

GTM의 진가는 세 가지 데이터를 연관(Correlation)지어 탐정처럼 장애를 추적할 때 나타납니다.

```
[메트릭 이상 감지] ➔ [트레이스 병목 추적] ➔ [로그 원인 파악]
```

1. **1단계 (Metrics):** 
	- Grafana 대시보드에서 `Mimir`를 통해 API 응답 시간이 갑자기 5초로 튀거나 에러율이 급증하는 것을 감지합니다.
2. **2단계 (Traces):** 
	- 해당 시점의 느렸던 요청을 `Tempo`에서 조회합니다. "A 서비스 ➔ B 서비스 ➔ DB 쿼리(4.8초 소요)"와 같이 어느 구간에서 병목이 생겼는지 직관적으로 확인합니다.
3. **3단계 (Logs):** 
	- 지연을 유발한 DB 쿼리 구간의 `Trace ID`를 클릭하여 `Loki`로 바로 이동한 뒤, 해당 순간에 출력된 정확한 예외(Exception) 로그 메시지를 확인하고 버그를 수정합니다.


## 어떤 상황에서 사용하면 좋을까?

- **MSA 구조에서 "도대체 어디서 느려지는지" 모를 때:** 
	- 여러 API 간의 호출 관계와 구간별 소요 시간을 한눈에 보여줍니다.
    
- **배포 후 간헐적으로 에러가 발생할 때:** 
	- 전체 로그를 뒤지지 않고, 에러 발생 시점의 트레이스 ID만 쫓아가 원인을 규명할 수 있습니다.
    
- **장애 발생 시 빠른 RTO(복구 시간)가 필요할 때:** 
	- 알림(Alerting)부터 원인 파악까지 1~2분 안에 단일 화면에서 끝낼 수 있습니다.
    
- **소규모 팀에서 모니터링 비용을 아끼고 싶을 때:** 
	- 가벼운 리소스로 높은 수준의 모니터링 체계를 구축할 수 있습니다.
