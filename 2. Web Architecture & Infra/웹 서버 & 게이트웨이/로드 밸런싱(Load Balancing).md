## 왜 필요한가?

- 대규모 트래픽 환경에서 단일 서버의 자원 한계를 극복하기 위해, **여러 대의 서버(Scale-out)로 요청을 분산하여 시스템의 안정성과 성능을 극대화**하는 기술이다.

1. **과부하 방지 (성능 최적화):** 트래픽을 여러 서버로 적절히 나누어 특정 서버에 부하가 집중되는 현상을 막고, 사용자에게 빠른 응답 속도를 유지한다.
2. **고가용성 확보 (무중단 서비스):** 로드밸런서가 뒤편 서버들의 상태를 주기적으로 감시(Health Check)하여, 장애가 발생한 서버를 감지하면 해당 서버를 제외하고 정상 서버로만 요청을 전달한다.
3. **유연한 확장성 (Scalability):** 서비스 중단 없이 새로운 서버를 추가하거나 제거할 수 있어, 비즈니스 성장에 유연하게 대응할 수 있다.

## 정의 및 구현 방식

로드밸런싱은 물리적인 전용 네트워크 장비를 통해 구축하거나, 범용 서버에 고성능 소프트웨어를 설치하여 구현할 수 있다.

- **하드웨어 로드밸런서 (L4/L7 스위치):** 
  - 전용 하드웨어 장비(랙 장비)를 통해 대용량 네트워크 트래픽을 L4(TCP/UDP 주소 기반) 혹은 L7(HTTP/Application 프로토콜 기반) 레이어에서 하드웨어 칩셋 수준으로 정밀하게 처리한다. 안정성이 매우 높으나 장비 도입 및 유지보수 비용이 매우 비싸다.
- **소프트웨어 로드밸런서 (Nginx, HAProxy, Cloud LB 등):**
  - 일반 서버에 Nginx, HAProxy 같은 역방향 프록시(Reverse Proxy) 및 업스트림(Upstream) 라우팅 기능이 탑재된 프로그램을 실행하여 구현한다. 
  - 현대의 소프트웨어 로드밸런서는 하드웨어 장비에 밀리지 않는 고성능 처리 능력을 갖추고 있으며, 클라우드 환경(AWS ALB/NLB 등)에서 유연하게 아키텍처를 변경하고 확장할 수 있다는 독보적인 장점을 가진다.

## 동작 과정 및 헬스 체크의 실무적 한계

### ⚠️ 주기적 헬스 체크(Health Check)의 진실
- 로드밸런서는 타겟 서버에 주기적으로 요청을 보내 상태를 확인하지만, **장애를 실시간으로 '즉시' 알아차리는 것은 아니다.** 
- 예를 들어 5초 주기로 헬스 체크를 수행한다면, **서버가 다운된 순간부터 로드밸런서가 이를 감지하여 목록에서 격리하기 전까지의 수 초간의 공백기(Window)**가 발생한다. 이 짧은 시간 동안 장애 서버로 진입한 사용자의 요청은 실패할 수 있다. 
- 이를 방지하기 위해 실무에서는 "요청 전달 실패 시 즉시 다른 정상 서버로 재시도(Failover)"하는 백업 설정(`proxy_next_upstream` 등)을 연동해야 완벽한 무중단을 달성할 수 있다.

### 🛠️ Nginx 로드밸런싱 아키텍처 구성 예시

앞단에 Nginx 1대를 두고, 뒷단의 FastAPI 애플리케이션 3대로 부하를 분산하는 설정이다.

```nginx
# 1. 부하를 분산 처리할 WAS 서버들을 하나의 그룹으로 묶음 (Upstream 블록)
upstream my_was_cluster {
    server 192.168.0.10:8080 max_fails=3 fail_timeout=10s;  # 1번 WAS
    server 192.168.0.11:8080 max_fails=3 fail_timeout=10s;  # 2번 WAS
    server 192.168.0.12:8080 max_fails=3 fail_timeout=10s;  # 3번 WAS
}

server {
    listen 80; # 클라이언트가 진입하는 포트

    location / {
        # 2. 클라이언트 요청 진입 시 위에서 지정한 WAS 그룹으로 라우팅 (Reverse Proxy)
        proxy_pass http://my_was_cluster;
        
        # 3. 헬스 체크의 한계를 보완하기 위한 에러 발생 시 다음 서버 재시도 설정
        proxy_next_upstream error timeout invalid_header http_500 http_502;
    }
}
```

## 소프트웨어 로드밸런서 비교 (Nginx vs Apache)

- **Apache HTTP Server:** 
  - 전통적인 프레임워크 구조로, 미리 프로세스나 스레드를 풀(Pool) 형태로 대량 생성해 두고 요청을 할당하는 **MPM(Multi-Processing Module)** 구조로 동작한다. 현대의 `Event MPM` 도입으로 동시성 성능이 대폭 개선되었으나, 구조적 특성상 커넥션이 폭발하는 극한의 상황에서는 Nginx에 비해 메모리 점유율이 높아질 수 있다.
- **Nginx:** 
  - 비동기 **이벤트 주도(Event-Driven) 구조**로 설계되어, 극소수의 마스터/워커 프로세스만으로 수만 명의 동시 접속 커넥션을 대기(Non-blocking) 상태로 가볍게 유지할 수 있다. 대규모 리버스 프록시 및 로드밸런싱 환경에서 자원 효율성이 매우 뛰어나 시장에서 널리 선택받고 있다.

## 프로젝트에서는 어디에서 사용하는가?

- 현재 로컬 개발 환경(단일 인스턴스)에서 기능을 검증 중이므로 별도의 로드밸런서는 도입하지 않았다.
- 향후 운영 서버 아키텍처 확장 시, 클라우드가 제공하는 고성능 로드밸런서(ALB)를 앞단에 배치하여 대규모 트래픽 분산 처리를 수행할 예정이다.
