## 왜 필요한가?

- **인터페이스의 표준화:** 파이썬 자체로도 내장 모듈(`http.server`)을 통해 HTTP 요청을 직접 수신하고 해석할 수 있다. 하지만 과거에는 웹 서버(Apache, Nginx 등)와 파이썬 프레임워크(Django, Flask 등)를 연결하는 방식이 제각각이어서 호환성 문제가 심각했다.
- **상호 운용성 확보:** WSGI라는 일관된 연결 표준 규격이 등장하면서, 개발자는 프레임워크 종류와 관계없이 어떤 WSGI 서버(Gunicorn, uWSGI 등) 위에서도 안정적으로 앱을 구동할 수 있게 되었다.
- **미들웨어 확장성:** 표준 규약을 중간에 삽입하기 때문에, HTTP 요청이 파이썬 프로그램에 도달하기 전후에 공통 작업(인증, 로깅, 세션 처리 등)을 수행하는 미들웨어를 쉽게 끼워 넣을 수 있다.

## 정의

- **WSGI(Web Server Gateway Interface)**는 파이썬 웹 애플리케이션과 웹 서버가 서로 통신할 수 있도록 정의한 **동기식 인터페이스 표준 규격**이다.

1. **소프트웨어가 아닌 표준 문서:** WSGI는 다운로드하여 설치하는 프로그램이 아니라, 파이썬 제안서(PEP 3333)에 명시된 약속이자 규칙이다.
2. **동기식 요청-응답 모델:** 요청이 들어오면 하나의 실행 흐름(Thread/Process)을 점유하여 처리가 끝날 때까지 블로킹(Blocking)되는 구조를 가진다.
3. **코드 레벨의 정의 (Callable):** 파이썬 언어 관점에서 WSGI 애플리케이션은 **[두 개의 인자(`environ`, `start_response`)를 받고 반복 가능한 객체(Iterable)를 반환하는 콜러블(Callable: 함수나 메서드)]** 인터페이스로 구현된다.

## 동작 과정

```
[Browser] ──(HTTP 요청)──> [Web Server] ──(CGI/소켓)──> [WSGI Server] ──(Callable 호출)──> [Python App]
```

1. **Client의 HTTP Request:** 브라우저가 네트워크를 통해 HTTP 요청 메시지를 보낸다. 
2. **웹 서버(Nginx, Apache 등)의 수신:** 정적 컨텐츠는 웹 서버가 직접 처리하고, 동적 컨텐츠 요청은 뒤편의 WSGI 서버(Gunicorn 등)로 토스한다. 
3. **WSGI 서버의 데이터 변환:** HTTP 환경 변수와 요청 데이터를 파이썬이 다룰 수 있는 가독성 높은 딕셔너리(`environ`) 객체로 변환한다. 
4. **파이썬 앱(Framework) 호출:** WSGI 서버가 파이썬 웹 프레임워크의 진입점(Callable)을 호출하며 로직을 실행한다. 
5. **동기식 응답 반환:** 애플리케이션이 응답 데이터를 반환하면 WSGI 서버와 웹 서버를 거쳐 클라이언트에게 전달된다. (※ 이때 HTTP/1.1 사양에 따라 TCP 연결은 바로 끊기지 않고 `Keep-Alive`로 유지될 수 있다.) 

## ASGI와의 차이점 

| 비교 항목        | WSGI                                                               | ASGI                                              |
| ------------ | ------------------------------------------------------------------ | ------------------------------------------------- |
| **처리 모델**    | **동기식(Synchronous)** 요청-응답 구조                                      | **비동기식(Asynchronous)** 메시지 송수신 구조                 |
| **지원 프로토콜**  | 단일 HTTP 요청-응답 프로토콜 중심                                              | HTTP 외에도 **WebSockets**, gRPC 등 다양한 프로토콜 확장 표준 지원 |
| **I/O 아키텍처** | 1 요청이 1 스레드/프로세스를 점유하여 처리                                          | **이벤트 루프** 기반으로 싱글 스레드에서도 수많은 연결 동시 처리            |
| **데이터 처리**   | **동기식 스트림 방식**으로 청크 단위 처리가 가능 (`wsgi.input` 및 `yield` 응답 제너레이터 활용) | **비동기 스트리밍** 방식을 활용하여 대용량 입출력 시 자원 효율 극대화         |
| **대표 프레임워크** | Django (기본), Flask, Pyramid                                        | FastAPI, Django Channels, Starlette               |
