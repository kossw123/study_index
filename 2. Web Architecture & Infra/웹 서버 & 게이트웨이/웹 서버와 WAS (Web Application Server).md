## 왜 필요한가?

- **효율적인 역할 분담:** 클라이언트의 유입 경로 통제, 보안, 캐싱 등의 인프라 레이어 제어와 실제 비즈니스 도메인 로직 및 데이터 처리를 담당하는 애플리케이션 레이어를 분리하여 시스템의 안정성과 확장성을 높이기 위해 필요하다.

## 정의 및 기능의 중첩

전통적으로 웹 서버와 WAS는 처리하는 콘텐츠(정적 vs 동적)로 구분해 왔으나, **현대 웹 아키텍처에서는 두 제품군의 기술적 기능이 대거 겹쳐 있으며 상호 보완적으로 작동**한다.

### 1. 웹 서버 (Web Server)
- **전통적 역할:** 클라이언트의 HTTP 요청을 직접 받아 서버 디스크에 저장된 정적 콘텐츠(HTML, CSS, JS, 이미지 등)를 빠르게 전송한다.
- **현대적 확장 (인프라 제어 핵심):** 정적 파일 제공에만 국한되지 않는다. 앞단에서 클라이언트 요청을 맞이하는 **리버스 프록시(Reverse Proxy), 로드 밸런싱, SSL/TLS 암호화 복호화(인증서 관리), 대용량 요청 버퍼링 및 보안(DDoS 방어 등)**의 중추적인 인프라 제어 역할을 수행한다. (예: Nginx, Apache HTTP Server 등)

### 2. WAS (Web Application Server)
- **전통적 역할:** 웹 서버가 토스해 준 요청을 받아 비즈니스 로직(코드)을 구동하고, 데이터베이스(DB)와 연동하여 실시간으로 가공된 동적 콘텐츠를 생성 및 반환한다.
- **현대적 확장 (독립적 구동 가능):** 현대의 WAS 제품군(Uvicorn, Gunicorn, Tomcat 등)은 고성능 HTTP 웹 서버 엔진을 자체 내장하고 있다. 따라서 **앞단에 별도의 웹 서버를 두지 않더라도 단독으로 정적 파일 서빙과 동적 로직 처리를 모두 완벽하게 수행**할 수 있다.

> **💡 핵심 요약: 기계나 제품의 구분이 아닌 '역할의 분담'**
> 현대 아키텍처에서 두 개념은 제품의 절대적인 한계를 뜻하지 않는다. WAS 단독으로도 웹 서비스를 완벽히 구동할 수 있지만, 운영 환경에서 웹 서버(Nginx 등)를 앞단에 붙이는 이유는 **보안 강화, 무중단 배포를 위한 로드 밸런싱, Slow Client 차단 등 웹 서버가 가진 인프라 제어 기술을 레버리지하기 위함**이다.

## 프로젝트에서는 어디에서 사용하는가?

- **현재 구조 (개발 및 검증 단계):** 
  현재는 ASGI 고성능 서버 엔진인 **Uvicorn(WAS)**이 자체 내장 웹 서버 기능을 활용해 클라이언트의 HTTP 요청 접수부터 FastAPI 비즈니스 로직 연동, 정적/동적 응답 처리를 모두 단독으로 도맡아 수행하고 있다.
- **향후 구조 (프로덕션 배포 단계):** 
  운영 서버 환경으로 확장 시에는 보안 향상 및 무중단 배포 아키텍처 구축을 위해 앞단에 **Nginx(웹 서버/리버스 프록시)**를 배치하고, 뒷단에 **Uvicorn+FastAPI(WAS/애플리케이션)** 인스턴스를 다수 배치하는 협력 구조로 전환할 예정이다.
