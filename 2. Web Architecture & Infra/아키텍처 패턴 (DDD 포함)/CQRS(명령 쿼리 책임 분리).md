## 왜 필요한가?

설계 측면에서 본다면 기존의 CRUD 구조는 보통 하나의 클래스나 API에서 create, read, update, delete를 전부 처리한다.
기존 CRUD 구조의 문제는 단순히 하나의 클래스나 API에서 다 처리하는 것을 넘어, "쓰기(CUD)를 위한 데이터 형태와 읽기(R)를 위한 데이터 형태"가 완전히 다르다.

CUD는 데이터의 정확성, 무결성, 비즈니스 규칙 검증이 중요하지만,
R는 비즈니스 로직 없이 그냥 화면에 맞는 데이터를 보여주는 속도가 중요하다.


## 정의

Command Query Responsibility seperate

CQRS 패턴에서는 다음과 같이 정의한다.

Command는 시스템의 상태를 변경하는 `명령`이다.
Query는 시스템의 상태를 조회만 하는 `작업`이다.

## 장점

1. 성능 최적화
	- 쓰기용 DB는 복잡한 JOIN이 없는 정규화된 구조로 유지하고, 읽기용 DB는 JOIN이 필요없도록 미리 가공(비정규화)된 데이터를 둬 조회를 비약적으로 빠르게 만든다.
2. 독립적 확장
	- 쓰기보다 조회가 많은 서비스에 읽기 서버와 쓰기 서버를 독립적으로 분리하여 트래픽에 맞춰 유연하게 확장할 수 있다.
3. 복잡성 감소
	- 하나의 모델에 CRUD의 요구사항을 전부 넣을 필요가 없어서, 복잡하고 거대한 코드를 방지할 수 있다.

## 단점

1. 데이터 동기화(지연)
	- 쓰기 DB의 데이터가 읽기 DB로 전달되기까지의 시간 차이가 발생할 수 있다.
		- 이를 최종 일관성(Eventual Consistency)라 부른다.
	- 실시간성이 매우 중요한 시스템에서는 설계가 까다로워 진다.
2. 구축 및 아키텍처 복잡성
	- 저장소와 모델이 분리되면서 메시지 브로커(Apache, Kafka 등)나 동기화 배치 프로그램 등 추가적인 인프라가 필요해서 시스템 복잡도가 올라간다.

## 활용 분야

- 읽기, 쓰기 작업의 비율이 극도로 비대칭적인 시스템
	- 뉴스 인사이트, 듀오링고 등
- 복잡한 통계, 대시보드, 리포팅 화면이 많이 필요한 시스템
- 복잡한 도메인 모델을 다루는 엔터프라이즈 급 애플리케이셔ㅑㄴ

## 하는 방법

주로 이벤트 기반 아키텍처(Event-Driven Architecture)를 사용한다.

- **[쓰기]** 사용자가 데이터 수정 명령을 내립니다.
- **[쓰기 저장소]** 명령 핸들러가 비즈니스 로직을 검증하고 데이터를 쓰기 전용 DB에 반영합니다.
- **[이벤트 발행]** 데이터가 변경되었다는 이벤트(Event)를 생성하여 발행(Publish)합니다.
- **[이벤트 구독 및 반영]** 프로젝터(Projector) 또는 컨슈머(Consumer)가 이벤트를 받아 읽기 전용 DB를 갱신합니다
