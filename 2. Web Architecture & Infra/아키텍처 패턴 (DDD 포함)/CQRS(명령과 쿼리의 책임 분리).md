## 왜 필요한가?

- **[단일 모델의 단점 극복]**
    - 전통적인 CRUD 구조는 하나의 데이터 모델이나 API 클래스에서 쓰기(CUD)와 읽기(R)를 모두 처리한다.
    - 하지만 시스템이 커질수록 "쓰기를 위한 도메인 규칙"과 "읽기를 위한 UI 화면 요구사항"이 얽혀 코드가 비대되거나 어느 한쪽의 성능이 타협받는 문제가 발생한다.
    - 
- **[관점의 차이 인정]**
    - **CUD(명령):** 데이터의 정확성, 무결성, 강력한 비즈니스 규칙 검증이 최우선이다.
    - **R(조회):** 화면에 최적화된 데이터를 필요한 포맷으로, 권한 검사나 업무상 계산을 거쳐 최대한 빠르게 제공하는 것이 최우선이다.

## 정의

Command Query Responsibility Segregation (명령 조회 책임 분리)

> 시스템에서 데이터를 변경하는 주체(Command)와 데이터를 조회하는 주체(Query)의 **소스 코드 구조와 책임을 분리**하는 아키텍처 패턴이다.

- **Command (명령):** 시스템의 상태를 변경하는 연산 (Return 값이 없거나 최소한의 ID만 반환, 비즈니스 로직 집중).
- **Query (조회):** 시스템의 상태를 반환하는 연산 (상태를 변경하지 않음, **UI 렌더링을 위한 권한 검증 및 업무상 계산 포함 가능**).

## 장점

1. **성능 최적화 가능성**
    - 데이터 모델을 분리하면 복잡하게 쪼개진 **정규화된 쓰기 모델(JOIN이 많이 필요함)**과, 조회에 최적화되어 미리 가공된 **비정규화된 읽기 모델(JOIN이 없거나 적음)**을 독립적으로 설계하여 복잡한 조회 성능을 비약적으로 높일 수 있다.
2. **독립적 확장성**
    - 아키텍처를 고도화하여 서버나 데이터베이스를 물리적으로 분리할 경우, 통상적으로 쓰기보다 요청이 수십~수백 배 많은 조회(Query) 트래픽에 대응해 읽기 전용 인프라만 유연하게 확장할 수 있다.
3. **도메인 복잡성 감소**
    - 하나의 객체에 CUD와 R의 요구사항을 억지로 욱여넣지 않아도 되므로, 핵심 비즈니스 로직 코드와 조회 전용 코드가 깔끔하게 분리되어 유지보수가 쉬워진다.

## 단점 및 고려사항

1. **구축 및 유지관리 비용 상승**
    - 구조가 명확해지는 대신 작성해야 할 클래스와 코드의 양이 늘어납니다. 단순한 CRUD 시스템에 적용하면 오히려 오버헤드가 될 수 있다.
2. **인프라 확장의 양날의 검 (물리 분리 시)**
    - **만약 성능을 위해 쓰기 DB와 읽기 DB를 물리적으로 분리한다면**, 두 저장소 간의 데이터 동기화 메커니즘(이벤트 발행, 동기화 배치 등)이 필요하여 시스템 복잡도가 크게 올라간다.
    - 이 과정에서 데이터가 복사되는 찰나의 시간 차이가 발생하는 **최종 일관성(Eventual Consistency)** 문제가 생기므로, 실시간성이 극도로 중요한 비즈니스에서는 설계가 매우 까다로워진다.

## 구현 단계 (동작 방식의 분류)

CQRS는 시스템의 규모와 복잡도에 따라 단계별로 구현할 수 있다.

- **1단계: 애플리케이션 수준 분리 (기본)**
    - 단일 DB를 공유하되, 소스 코드 내에서 CUD를 처리하는 서비스/엔티티 클래스와, R을 처리하는 조회용 데이터 객체(DTO/QueryService)를 완전히 분리한다.
- **2단계: 데이터베이스 수준 분리 (고도화)**
    - 데이터베이스를 쓰기 전용(Master)과 읽기 전용(Replica)으로 분리하여 부하를 분산한다.
- **3단계: 이벤트 기반 아키텍처와 통합 (엔터프라이즈)**
    - 쓰기 DB와 읽기 DB의 종류(예: RDB와 NoSQL/Redis)마저 다를 때 주로 사용한다. Command 측에서 데이터 변경 시 이벤트를 발행하면, 이를 구독하는 프로세서가 읽기 전용 저장소를 동기화(프로젝션)한다.

## 활용 분야

- 읽기, 쓰기 작업의 비율이 극도로 비대칭적인 시스템
	- 뉴스 인사이트, 듀오링고 등
- 복잡한 통계, 대시보드, 리포팅 화면이 많이 필요한 시스템
- 복잡한 도메인 모델을 다루는 엔터프라이즈 급 애플리케이션

## 하는 방법

주로 이벤트 기반 아키텍처(Event-Driven Architecture)를 사용한다.

- **[쓰기]** 사용자가 데이터 수정 명령을 내립니다.
- **[쓰기 저장소]** 명령 핸들러가 비즈니스 로직을 검증하고 데이터를 쓰기 전용 DB에 반영합니다.
- **[이벤트 발행]** 데이터가 변경되었다는 이벤트(Event)를 생성하여 발행(Publish)합니다.
- **[이벤트 구독 및 반영]** 프로젝터(Projector) 또는 컨슈머(Consumer)가 이벤트를 받아 읽기 전용 DB를 갱신합니다
