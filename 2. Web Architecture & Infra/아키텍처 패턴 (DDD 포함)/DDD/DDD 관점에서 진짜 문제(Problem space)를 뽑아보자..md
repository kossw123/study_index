
## DDD에서 말하는 문제란 무엇인가?
- 화면 흐름
- 유스케이스 단계
- 기능 목록
  
전부 아니다.

> DDD에서 문제는 단순한 기능 목록이나 UI 화면 흐름을 넘어, 비즈니스가 해결하고자 하는 현실 세계의 복잡성과 달성하려는 목표의 집합을 의미한다.  
> 
> 특히 그 안에서 "비즈니스가 안전하게 성립하기 위해 절대 깨지면 안 되는 핵심 규칙(불변식)"을 찾아내는 것이 문제 분석의 핵심이다.

대부분 처음에는 자연어를 분해한다.

> "주문 받은 상품을 만들고, 결제하고, 적립한다"


### 진짜 문제를 도출하기 위한 유용한 접근법: 역발상 분석

그러나 이건 요구사항이지, 문제가 아니다.
DDD에서는 여기서 관점을 반대로 뒤집는다.

> 즉, 요구사항을 금지해야하는 사항으로 바꾼다.

- 허용 금지의 경계
- 사고 발생 조건

아래와 같은 문장으로 정리할 수 있다.

> "이 흐름 중에서 잘못되는 가장 큰 사고는 무엇인가?"

---
- 긍정적인 유스케이스 흐름 뒤에 숨겨진 **'사고 발생 조건(실패 시나리오)'** 을 질문 던짐으로써, 비즈니스의 핵심 제약사항을 더 명확하게 드러낼 수 있다. 
- (단, 이는 불변식을 찾기 위한 강력한 분석 도구 중 하나이며, 비즈니스의 동적인 시간 흐름이나 이벤트 역시 DDD의 중요한 분석 대상이다.)
---
## Problem space를 뽑는 과정

1. **["실패 했을 때 결과"를 먼저 적는다.]**
	- 이게 실패하면 무슨 일이 벌어지는가?
	- 결제가 두 번 승인되면?
	- 승인 안 된 결제가 적립되면?
	- 판매 불가 상품이 주문 되면?

```
여기서 부터 진짜 문제가 나온다.
```


2. **[실패를 "누가 막아야 하는가?"로 바꾼다.]**

실패 시나리오를 막기 위한 주체를 뽑아보자.

| 실패 상황       | 반드시 막아야 하는 주체   |
| ----------- | --------------- |
| 중복 결제       | Payment         |
| 판매 종료 상품 주문 | Product         |
| 결제 전 적립     | Reward          |
| 할인 규칙 위반    | Pricing, Policy |
```
이 순간 도메인이 추출된다.
> Payment, Product, Reward, Pricing(Policy)
```

### 개념 추출 시 주의할 점
  - 실패 상황을 막는 주체를 통해 도메인의 주요 개념(명사)**들을 유추할 수 있다. 
  - 하지만 문장 속 명사가 무조건 독립적인 애그리거트가 되는 것은 아니다. 
  - 비즈니스 규칙과 라이프사이클을 고려하여, 이 개념이 독립적인 애그리거트가 될지, 아니면 다른 애그리거트 내부의 속성(Entity나 VO)으로 포함될지 깊이 고민해야 한다.

3. **["이걸 막지 못하면 존재 이유가 없는 객체"를 찾는다.]**

```
"이 객체가 이걸 막지 못하면 이 객체는 왜 존재해야 하는가?"
```

이 질문은 DDD에서 강력하게 존재한다.

```
e.g)
Payment가 승인 불가를 말 못한다면? -> 그냥 계산기일 뿐이다.
Product가 판매 불가를 말 못한다면? -> 그냥 데이터다.
```

**그리고 이 질문에 답하는 순간, Aggregate가 보인다.**

4. **[문제를 불변식으로 변환한다.]**

```
e.g)
> 승인되지 않은 결제는 절대 금액 이동이 발생하지 않는다.
> 판매 불가 상품은 어떤 주문에도 포함될 수 없다.
```

5. **[불변식을 기준으로 경계를 자른다.]**

> DDD에서 경계는 **["하나의 트랜잭션에서 반드시 지켜야 하는 불변식의 묶음"]** 이다.

```
e.g)
중복 결제 방지 -> Payment Aggregate
판매 가능 여부 -> Product Aggregate
주문 상태의 일관성 -> Order Aggregate
```


## DDD 관점에 대한 내 생각들

[요구 사항에 따른 과점의 방향을 반대로 생각해보면 다음과 같다.]
- **"적립할 때는 결제되어선 안된다." **
	- 너무 시점으로 생각했다.
	- 이걸 DDD적으로 바꾼다면 다음과 같다.
		- "결제되지 않는 주문에서 적립이 되어선 안된다"
- **"결제 할때는 주문되어선 안된다."**
	- 너무 시점으로 생각했다.
	- 이걸 DDD적으로 바꾼다면 다음과 같다.
		- "주문이 존재하지 않으면 결제가 발생할 수 없다."

이런 요구사항과 문제를 착각하는 실수가 발생한 이유는 다음과 같다.

```
> 1. 요구사항을 부정하려 했다.
> 2. "무엇이 잘되면 사고인가?", "이 행동이 돈/신뢰/운영을 깨뜨리는가?"
```

> DDD에서 뒤집는 대상, 즉 금지사항으로 바꾸려는 대상은 시간, 순서, 흐름이 아니다.
> 오히려 반대인 허용, 금지, 사고 발생 조건이 대상이 되어야 한다.

```
e.g)
다음 문장을 DDD적으로 바꿔서 진짜 문제를 찾아보자.

"고객은 쿠폰을 발급받아 주문에 적용하고, 결제 후 포인트를 적립한다."

> 결제가 안되면 포인트가 적립되어선 안된다.
> 주문이 결제 될 때 적용되지 않은 쿠폰이 소모되어선 안된다.
> 쿠폰은 여러 주문에 적용되어선 안된다.

불변식을 기준으로 경계를 만들기 위해 무엇이 필요할까?

경계는 하나의 트랜잭션에서 동작되는 불변식의 묶음이다.
즉, DB와 통신하는 객체가 가지는 불변식들의 묶음이다.

> 첫 번째 문장에서는 
> 	결제(Payment), 포인트(Point)라는 Aggregate를 발견했다.
> 두 번째 문장에서는 
> 	주문(Order), 결제(Payment), 쿠폰(Coupon) 이라는 Aggregate를 발견했다.
> 세 번째 문장에서는 
> 	쿠폰(Coupon), 주문(Order)라는 Aggregate를 발견했다.

이런식으로 총 결제(Payment), 포인트(Point), 주문(Order), 쿠폰(Coupon)이라는 Aggregate를 발견했다.

> DDD에서 애그리거트(Aggregate)는 "비즈니스 규칙 상 하나의 단위로 묶여서 항상 일관성을 유지해야 하는 불변식의 최소 경계"이다.  
> 기술적으로는 '하나의 트랜잭션으로 처리되는 단위'가 되지만, 본질은 DB 구조가 아니라 비즈니스 논리의 일관성을 지키기 위한 경계이다.

```
