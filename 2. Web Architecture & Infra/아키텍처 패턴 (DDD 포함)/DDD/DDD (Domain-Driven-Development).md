## 왜 필요한가?

- 소프트웨어의 복잡성을 낮추고 요구사항을 정확하게 반영하기 위해서다.

- **[1. 비즈니스 복잡성의 효과적인 제어]**
    - [1. 문제 영역의 분리]
        - 대규모 시스템의 복잡한 요구사항을 하위 도메인 단위로 쪼개서 문제를 단순화한다.
    - [2. 명확한 경계 설정]
        - 바운디드 컨텍스트를 통해 특정 모델과 용어가 영향을 미치는 경계를 확실히 구분한다.
    - [3. 모델 오염 방지]
        - 서로 다른 비즈니스 영역 간의 데이터가 엉키는 것을 막아 시스템의 결합도를 낮춘다.
- **[소통 비용 및 오해 감소]**
    - [1. 보편언어(Ubiquitous Language)]
        - 개발자, 기획자, 비즈니스 전문가가 모두 같은 용어를 사용한다.
    - [2. 의사소통 오류 차단]
        - 요구사항이 코드로 번역되는 과정에서 오해와 왜곡을 감소시킨다.
    - [3. 코드의 문서화]
        - 코드가 곧 문서화가 되게끔하여 DOCS를 작성할 필요가 거의 없다.
- **[높은 유지보수성과 확장성 보장]**
    - [1. 핵심 로직의 보호]
        - DB나 외부 API 같은 기술적 세부사항을 도메인 로직과 분리시킨다.
    - [2. 변화에 유연함]
        - 비즈니스 규칙이 변경되어도, 유비쿼터스 언어로 제작된 도메인은 다른 레이어에 영향을 줄 필요 없이, 핵심 도메인만 수정하면 된다.
    - [3. MSA와 높은 궁합]
        - 바운디드 컨텍스트가 그대로 MSA의 경계가 될 수 있다.


## 정의

- 개발에서 비즈니스 문제 영역을 뜻하는 도메인을 중심에 두고 개발을 진행하는 방법론이다.

## 동작 과정

보통 비즈니스 전문가와 전체적인 비즈니스 지도를 그리고 경계를 나누는 데, 두 가지 부분으로 나누는게 평균이다.

> 전략적 설계 (Strategic design)

- 도메인 이벤트 도출
- 바운디드 컨텍스트(Bounded Context) 정의
- 보편 언어(Ubiquitous Language) 정의
- 컨텍스트 맵(Context map) 작성

> 전술적 설계 (Tactical design)

- 애그리거트(Aggregate) 정의
- 엔티티(Entity)와 밸류 객체(Value Object: VO) 구분
- 도메인 서비스(Application Layer 구현
- 리포지토리 설계


## 보통 DDD에서 사용하는 구조

```
Framework, DB, UI, External Systems
 ↓
infrastructure
 ↓
application
 ↓
domain
```

보통 이런식으로 프로그램이 동작한다.

## 프로젝트 어디에서 사용하는가?

- 대규모 시스템, 엔터프라이즈급의 시스템에서 사용자의 요구사항이 복잡할 때 적용할 수 있는 방법론이다.
