## 정의

> DDD에서는 도메인을 다음과 같이 정의한다.

### [1. 세상은 “도메인”이다.]

- **도메인 (Domain):** 소프트웨어로 해결하고자 하는 **현실 세계의 비즈니스 활동 범위와 지식 영역 그 자체** (예: 이커머스, 물류, 금융)
- **도메인 모델 (Domain Model):** 해당 도메인의 복잡성을 해결하기 위해 **특정 목적에 맞춰 단순화하고 추상화한 개념적 모형** (현실의 복사본이 아닌, 의사결정을 위한 템플릿)
- **도메인 객체 (Domain Object):** 도메인 모델을 반영하여 **실제 코드로 구현된 엔티티(Entity)나 밸류 객체(Value Object)**

---

```
보통 CRUD 중심 사고로 개발되지만, DDD는 아래 조건을 중심으로 사고한다.
> 1. 이 상태 변화는 허용되는가?
> 2. 누가(Who), 언제(When), 어떤 조건(What condition)에서 상태가 변할 수 있는가?
```

> DDD 관점에서는 도메인은 코드보다 먼저 존재하기 때문에, 다음과 같이 사고한다.
> 
> 1. 비즈니스에는 이미 규칙이 있다.
> 2. 우리는 그 규칙을 발견한다.
> 3. 코드는 그 규칙을 표현할 뿐이다.

### [2. 도메인은 ”현실의 복사“가 아니라 ”의사 결정 도구“다.]

- 현실과 똑같은 기능과 데이터를 복사한다 해도 시스템은 만들어지지 않는다.
- 그래서 보통 도메인을 작성하다 보면, 도메인 객체는 자기 상태를 자기 스스로가 결정, 즉 의사를 결정할 수 있다.

> 도메인은 스스로의 상태를 결정하기 때문에, 다음과 같은 특징을 가진다.
> 
> 1. 모든 것을 표현하지 않는다.
> 2. 중요한 제약, 불변 조건, 결정 포인트만 표현한다.
> 3. 왜 안되는지 코드로 설명한다.


### [3. 언제나 유효해야 하는 '불변식(Invariant)'을 기준으로 설계한다.]

- **[불변식:]**
	- 데이터가 바뀔 때 **"항상 올바른 상태를 유지하기 위해 만족해야 하는 비즈니스 제약 규칙"**을 의미한다.
	- 이 불변식을 깨뜨리지 않고 항상 일관성 있게 관리해야 하는 단위가 바로 **일관성 경계(Consistency Boundary)**이자 **애그리거트 경계(Aggregate Boundary)**가 된다.

```
"언제부터 절대 변해서는 안되는가?"

DDD에서는 보통 이 순간을 다음과 같이 부른다.
> Invariant (불변조건)
> Consistency Boundary (일관성 경계)
> Aggregate Boundary (집합 경계)의 근거
```

> 상태는 "무엇을 할 수 있다"가 아니라 "무엇이 금지된다"에서 갈라진다.


### [4. 상태는 DB Column 같은 실제 데이터가 아닌 의미의 경계다.]

- 의미적으로 더 이상 같은 규칙을 적용할 수 없는 경계를 의미한다.

> 다음과 같이 생각해보면 답을 쉽게 도출해낼 수 있다.
> 
> 1. 어째서 이 시점의 이전에는 허용되던 게
> 2. 왜 이 시점 이후에는 금지되는가?

- 상태가 변한다는 것은 정책의 분기점으로도 볼 수 있다.

### [5. 엔티티(Entity)는 식별자(Identity)와 책임(Responsibility)의 결합이다.]

- **식별성(Identity):** 
	- 엔티티는 내부 속성(데이터)이 완전히 바뀌더라도 고유한 식별자를 통해 **속성과 무관하게 동일한 객체로 인식**된다. 
	- (예: 사용자의 이름과 주소가 바뀌어도 '회원 ID'가 같다면 동일한 사용자다.)
- **생명주기와 연속성(Continuity):** 
	- 시스템 내에서 생성되어 상태가 변하다가 삭제되기까지의 흐름(Lifecycle)을 추적할 수 있다.
- **행위 중심 구조:** 
	- 단순히 데이터를 담는 그릇이 아니라, 자신이 가진 식별자와 관련된 비즈니스 규칙(불변식)을 스스로 검증하고 책임지는 행위 중심의 객체다.

---

|     | 일반적 사고             | DDD 관점 사고        |
| --- | ------------------ | ---------------- |
| 책임  | 이 객체는 무엇을 가지고 있는가? | 이 객체는 무엇을 책임지는가? |
| 데이터 | 어떤 필드를 가지고 있는가?    | 어떤 규칙을 지키게 하나?   |
| 구현  | setter가 필요하다.      | setter는 위험하다.    |

다음과 같은 코드를 예시로 들 수 있다.

```
product.change_price(new_price)

이 코드는 DDD 관점에서 보면 단순 가격 변경이 아닌,
> "지금 이 상품은 가격 변경이 가능한 상태인가?"
> "이미 판매가 시작되었는가?"
이런 항목들을 상품 스스로가 판단하고 변경되어야 한다.
```

### [6. Application은 조율자, Domain은 결정자]

DDD에서는 역할이 명확하게 갈린다.

- Application Layer
	- usecase 실행
	- transaction 관리
	- 여러 Aggregate를 포함
- Domain layer
	- 규칙 판단
	- 허용 / 차단 결정
	- 예외 발생

> 즉, Application Layer에서 "이걸 해달라"하면 Domain은 "된다/안된다(이유는 이것 때문이다.)"라고 대답하는 것이다.


### [7. Architecture는 목적이 아닌 결과다.]

- DDD를 한다고 해서 Hexagonal, Clean Architecture를 써야하는건 아니다.
- 그러나 Hexagonal, Clean Architecture는 DDD를 사용해서 만들 수 있다.
