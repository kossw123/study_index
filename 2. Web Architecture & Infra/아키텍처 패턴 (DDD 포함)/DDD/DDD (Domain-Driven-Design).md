## 왜 필요한가?

- 소프트웨어의 복잡성을 낮추고 요구사항을 정확하게 반영하기 위해서다.

- **[1. 비즈니스 복잡성의 효과적인 제어]**
    - [1. 문제 영역의 분리]
        - 대규모 시스템의 복잡한 요구사항을 하위 도메인 단위로 쪼개서 문제를 단순화한다.
    - [2. 명확한 경계 설정]
        - 바운디드 컨텍스트를 통해 특정 모델과 용어가 영향을 미치는 경계를 확실히 구분한다.
    - [3. 모델 오염 방지]
        - 서로 다른 비즈니스 영역 간의 데이터가 엉키는 것을 막아 시스템의 결합도를 낮춘다.
- **[소통 비용 및 오해 감소]**
    - [1. 보편언어(Ubiquitous Language)]
        - 개발자, 기획자, 비즈니스 전문가가 모두 같은 용어를 사용한다.
    - [2. 의사소통 오류 차단]
        - 요구사항이 코드로 번역되는 과정에서 오해와 왜곡을 감소시킨다.
    - [3. 코드의 의도 명확화]
        - 코드가 곧 문서화가 되게끔하여 DOCS를 작성할 필요가 거의 없다.
- **[높은 유지보수성과 확장성 보장]**
    - [1. 핵심 로직의 보호]
        - 비즈니스 용어를 코드로 그대로 반영하여(Self-documenting code) 코드만 보고도 비즈니스 로직을 쉽게 이해할 수 있도록 돕는다. 
        - (단, 전체 구조를 보기 위한 컨텍스트 맵이나 API 문서 등은 여전히 필수적이다.)
    - [2. 변화의 파급 효과 최소화]
        - 비즈니스 규칙이 변경되었을 때 인프라나 UI 레이어의 수정 없이 **도메인 레이어를 중심으로 변경 사항을 집중**시킬 수 있어, 비즈니스 요구사항 변화에 유연하고 안전하게 대응할 수 있다.
    - [3. MSA와 높은 궁합]
        - 바운디드 컨텍스트가 그대로 MSA의 경계가 될 수 있다.


## 정의

- 개발에서 비즈니스 문제 영역을 뜻하는 도메인을 중심에 두고 개발을 진행하는 방법론이다.

## 동작 과정

보통 비즈니스 전문가와 전체적인 비즈니스 지도를 그리고 경계를 나누는 데, 두 가지 부분으로 나누는게 평균이다.

> 전략적 설계 (Strategic design)

- 도메인 이벤트 도출
- 바운디드 컨텍스트(Bounded Context) 정의
- 보편 언어(Ubiquitous Language) 정의
- 컨텍스트 맵(Context map) 작성

> 전술적 설계 (Tactical design)

- 애그리거트(Aggregate) 정의
- 엔티티(Entity)와 밸류 객체(Value Object: VO) 구분
- 도메인 서비스(Application Layer 구현
- 리포지토리 설계


## DDD 아키텍처의 구조 (DIP 적용)

**1) 실행 흐름 (Runtime Flow):** 사용자의 요청이 인프라를 타고 도메인으로 들어오는 흐름
```
`UI/컨트롤러` ➔ `Application 서비스` ➔ `Domain 레이어` ➔ `Infrastructure(DB/외부API)`
```

**2) 의존성 방향 (Dependency Direction):** 모든 레이어가 핵심 비즈니스인 Domain을 향하는 구조 (의존성 역전)
```
[Infrastructure (DB, Web, UI, External)] 
	↓ (의존) 
[Application Layer] 
	↓ (의존) 
[Domain Layer] (최상위 중심, 의존성 없음)
```


```
Framework, DB, UI, External Systems
 ↓
infrastructure
 ↓
application
 ↓
domain
```

보통 이런식으로 프로그램이 동작한다.

## 프로젝트 어디에서 사용하는가?

- 대규모 시스템, 엔터프라이즈급의 시스템에서 사용자의 요구사항이 복잡할 때 적용할 수 있는 방법론이다.
