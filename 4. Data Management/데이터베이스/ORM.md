## 왜 필요할까?

- **객체 지향적 패러다임 유지:** 파이썬의 객체 중심 구조(Object)와 관계형 데이터베이스의 행렬 중심 테이블 구조(Relation) 간의 '패러다임 불일치'를 메타데이터 설정을 통해 중간에서 메워준다.
- **비즈니스 생산성 및 가독성 향상:** 단순 반복적인 CRUD 쿼리 문장을 개발자가 문자열로 일일이 하드코딩하지 않고, 객체의 메서드 형태로 자원을 안전하게 제어할 수 있어 백엔드 비즈니스 로직에만 집중할 수 있게 돕는다.

---

## 정의 및 실무적 한계에 대한 오해 교정

- **ORM (Object-Relational Mapping, 객체 관계 매핑)**은 객체 지향 프로그래밍 언어의 클래스와 관계형 데이터베이스(RDB)의 테이블을 자동으로 매핑하여 데이터 정합성을 맞춰주는 개발 인프라 시스템이다.

### ⚠️ [필독] 현업 아키텍처 관점에서의 ORM 기술 필터링

1. **런타임 데이터베이스 예외의 필연성:** 
   - 엔티티의 정적 타입은 코드 수준에서 1차 검증을 도울 뿐이다. 데이터베이스 연결 단절(Connection Timeout), 커넥션 풀 고갈, 고유 키 중복 위반(`IntegrityError`), 데드락(Deadlock) 등 치명적인 예외들은 **전부 프로그램이 구동되는 '런타임(Runtime)' 시점에만 발생**하므로, 철저한 예외 처리(Try-Catch 및 롤백 전략) 설계가 필수 수반된다.
2. **"SQL을 모르면 서버가 무너진다" (N+1 문제):**
   - ORM을 사용하더라도 **SQL 메커니즘을 완벽하게 알고 있어야 한다.** 내부 동작을 무시한 채 객체 참조를 남발하면 최악의 성능 병목인 **N+1 조회 쿼리 폭발 현상**이 발생한다. 내가 작성한 ORM 메서드가 뒤편에서 **어떤 Raw SQL로 직렬화되어 날아가는지 전 로그를 프로파일링하고 튜닝(Lazy Loading vs Fetch Join 선택 등)할 수 있는 역량**이 전제되어야 한다.
3. **스키마 마이그레이션(Migration)의 필요성:**
   - 비즈니스 요구사항에 따라 DB 스키마가 변경될 때 엔티티 클래스만 수정한다고 해서 물리 DB가 변하지 않는다. 엔티티 변경 본을 추적하여 실제 운영 데이터베이스 테이블에 안전하게 반영하기 위해서는 **Alembic 등의 스키마 형상관리 마이그레이션 파이프라인을 운영**해야 한다.
4. **DBMS 전환 시의 제약 조건:**
   - ORM이 데이터베이스 종속성을 완벽히 분리해 주지는 못한다. MySQL에서 PostgreSQL 등으로 엔진을 스위칭할 경우, 각 DBMS 고유의 **SQL 방언(Dialect), 특수 데이터 타입 호환성(JSONB 등), 트랜잭션 격리 수준(Isolation Level), 인덱스 거동 차이**를 철저히 검토하여 백엔드 코드를 동밀 튜닝해야 한다.

## 장점 및 단점

### 1. 장점
- **비즈니스 가독성:** 데이터 접근 로직이 순수 파이썬 코드로 표현되어 유지보수가 용이하다.
- **반복 코드 제거:** 테이블 컬럼 매핑 구조를 한 곳에서 관리하므로 휴먼 에러(오타)를 전면 차단한다.

### 2. 단점
- **성능 오버헤드:** 내부적인 SQL 자동 생성 알고리즘을 타기 때문에 복잡한 다중 조인(Join)문이나 대규모 대량(Bulk) 데이터 삽입/수정 시 텍스트 기반 Raw 쿼리 대비 처리 효율이 떨어질 수 있다. 이 경우 **QueryBuilder(Expression)를 쓰거나 특정 엔드포인트만 Raw SQL로 우회**하는 하이브리드 전략이 요구된다.

## 프로젝트 실무 적용 아키텍처

우리 프로젝트는 가독성과 타입 안정성을 모두 확보하기 위해 Pydantic과 SQLAlchemy의 장점을 결합한 최신 ORM인 **SQLModel**을 전면 채택하여 활용 중이다.

```
[Application Layer / Use Case]  
│  
▼  
[UnitOfWork (Transaction Guard)] ──(DB 세션 수명주기 통제)  
│  
▼  
[Repository Layer] ──(SQLModel ORM 구동) ──> [Database (MySQL)]
```

- **레포지토리 격리 (Repository Pattern):** 
	- 데이터베이스에 직접 자원을 조회하고 수정하는 모든 ORM 행위는 서비스 계층에 노출되지 않도록 `Repository` 객체 내부로 완전히 격리 은닉한다. 
- **트랜잭션 생명주기 관리 (UnitOfWork):** 
	- 레포지토리는 단지 ORM 명령을 예약할 뿐이며, 최종 비즈니스 성공 유무를 판단하여 단일 트랜잭션으로 커밋(`commit`)하거나 예외 발생 시 일괄 롤백(`rollback`)을 수행하는 책임은 `UnitOfWork` 컨텍스트 매니저가 전담하여 데이터 정합성을 철저히 방어한다.
