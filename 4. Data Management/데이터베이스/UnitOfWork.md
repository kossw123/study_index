## 왜 필요할까?

- **비즈니스 트랜잭션의 원자성(Atomicity) 보장:** 대규모 도메인 유스케이스를 처리할 때 여러 리포지토리에 걸쳐 수많은 데이터 변경(추가, 수정, 삭제)이 일어난다. 이때 일부 작업만 성공하고 일부는 실패하는 시나리오를 원천 차단하여 시스템의 일관성 경계를 완벽히 방어하기 위해 필요하다.
- **도메인 계층과 인프라 계층의 결합도 완화:** 애플리케이션 서비스가 비즈니스 로직 중간에 데이터베이스 커밋(`commit`)이나 롤백(`rollback`) 같은 구체적인 인프라 기술 명세에 종속되는 것을 막고, 트랜잭션 제어 책임을 별도의 아키텍처 레이어로 격리하기 위함이다.

## 정의

- **`UnitOfWork` (작업 단위 패턴)**는 단일 비즈니스 유스케이스 실행 과정에서 발생하는 **모든 데이터의 변경 사항(비즈니스 트랜잭션 내의 모든 CUD 작업)을 중앙에서 추적하고 기록했다가, 비즈니스가 완벽히 성공하는 최종 시점에 이를 모아 하나의 물리적 데이터베이스 트랜잭션 안에서 일괄 처리(조율)하는 디자인 패턴**이다.

---

## 동작 과정 및 올바른 기술적 필터링

```
[비즈니스 유스케이스 시작] ➔ UnitOfWork 컨텍스트 오픈  
│  
▼  
[도메인 로직 수행] ➔ 객체의 추가/수정/삭제 발생 (메모리 상태 변경 추적)  
│  
▼  
[유스케이스 최종 성공] ➔ UnitOfWork.commit() 원자적 호출  
│  
├─> 성공 시: 모든 변경 사항이 물리 DB에 일괄 저장됨 (Flush & Commit)  
└─> 실패 시: 예외 발생 즉시 전체 작업 무결성 취소 (Rollback)
```

### ⚠️ 백엔드 인프라 오해 바로잡기 

1. **커넥션 풀(Connection Pool)의 실제 점유 매커니즘:** 
	- 한 사용자의 요청 안에서 쿼리를 50번 실행한다고 해서 커넥션 풀의 통로 20개를 동시에 점유하는 것이 아니다. 일반적으로 하나의 HTTP 요청(혹은 단일 트랜잭션 스코프)은 **풀에서 단 '1개'의 커넥션만 대여**하여 사용한다. 그 1개의 통로를 끊지 않고 유지하며 50번의 쿼리를 순차적으로 주고받는 구조이다. 
	- 커넥션 풀 고갈은 다수의 동시 접속 유저가 각자 1개씩 커넥션을 물고 비즈니스 연산 지연으로 인해 풀에 반납하지 않을 때 발생하는 현상이다. 
2. **반복 쿼리 폭발(Chatty I/O)과 N+1 문제의 명확한 구분:** 
	- 루프문 등을 돌며 데이터를 반복해서 입력/수정하여 발생하는 네트워크 왕복 지연은 **채티(Chatty) I/O 병목** 또는 RTT(Round Trip Time) 오버헤드라고 부른다. 
	- **N+1 문제**는 데이터 입력이 아닌 **'조회 최적화 실패'** 현상이다. ORM 환경에서 부모 객체 1건을 조회한 후, 지연 로딩(Lazy Loading)으로 설정된 연관 자식 객체들의 상태를 참조하는 과정에서 자식 테이블에 N번의 불필요한 추가 조회 쿼리가 폭발하여 서버를 마비시키는 병목이다.

## 데이터베이스 자원 최적화를 위한 하이브리드 전략 

`UnitOfWork` 패턴으로 비즈니스 정합성을 묶어내면서, 물리적인 대용량 데이터 처리 병목이 예상될 때는 다음과 같은 특화된 인프라 최적화 기술들을 결합하여 아키텍처를 방어한다. 
### 1. 벌크(Bulk) 연산의 확장된 명세 
- **본질:** 
- 영속성 컨텍스트의 메모리 변경 추적(Dirty Checking)과 개별 도메인 유효성 검사 단계를 완전히 우회하고, 데이터베이스 스토리지 엔진에 대량의 데이터를 다이렉트로 내려쓰는 고속 인프라 기술이다. 
- **형태의 다양성:** 
- 단일 SQL 문장으로 묶는 `Multi-row INSERT` 구문뿐만 아니라, 준비된 쿼리를 메모리 버퍼에 쌓아 한 번에 전송하는 드라이버 레벨의 `Batch Execution`, 대용량 파일을 바이너리로 고속 복사하는 `COPY` 명령 등 비즈니스 사양에 따라 다채롭게 구현된다. 
### 2. 즉시 로딩 (Eager Loading) 전략 
- 데이터가 파편화되어 여러 번 서빙되는 것을 막기 위해 하위 연관 데이터를 최초 조회 시점에 한꺼번에 가져오는 기법이다. 
- 무조건 단일 `JOIN` 쿼리만 고집하는 것이 아니며, 네트워크 전송 데이터의 중복 뻥튀기를 방지하기 위해 상위 ID 배열을 가지고 `IN` 절 기반의 **최적화된 다중 쿼리 시퀀스를 쏘아 즉시 조립하는 전략**도 실무에서 매우 핵심적으로 활용된다. 
### 3. 캐싱 (Caching) 
- 자주 조회되지만 데이터 정합성 변화 주기가 길고 무거운 자원은 인메모리 키-값 저장소인 **Redis** 레이어에 격리하여, 메인 RDB로 향하는 읽기(Read) 트래픽 인프라 부하를 전면 차단한다.

## 프로젝트에서는 어디에서 사용하는가? 
- **DDD 계층 간 트랜잭션 가드:** 
	- 우리 백엔드 프로젝트의 `Application Layer` 유스케이스 구현부 전반에서 데이터의 원자성 확보를 위해 사용된다. 
- **SQLModel 인프라 조율:** 
	- 레포지토리 계층(`Repository`)은 단지 SQLModel ORM의 상태 변경만 예약하며, 유스케이스 종료 시점에 예외가 없음을 확인하고 SQLAlchemy 세션을 안전하게 커밋하여 자원을 일괄 반납하는 **`with...yield` 기반의 통합 UnitOfWork 파이프라인**을 구축하여 활용하고 있다.
