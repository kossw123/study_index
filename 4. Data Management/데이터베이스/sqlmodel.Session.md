## 왜 필요할까?

- **비즈니스 대화 창구 및 영속성 컨텍스트 관리:** 
	- 백엔드 어플리케이션 소스코드와 실제 데이터베이스 엔진 사이에서 데이터를 주고받는 유일한 논리적 소통 관문 역할을 수행한다.
- **트랜잭션의 경계 설정:** 
	- 하나의 유스케이스 안에서 발생하는 연산들을 단일 물리 트랜잭션 단위로 묶어 관리함으로써 데이터의 일관성과 원자성을 확보하기 위해 필요하다.

## 정의

- **`sqlmodel.Session`**은 데이터베이스에 대한 단일 논리적 연결 스코프를 나타내며, 내부 영속성 컨텍스트의 상태 변화를 추적하고 데이터베이스 **DML(데이터 조작어: 데이터 조회, 삽입, 수정, 삭제) 및 트랜잭션 제어 행위를 전담하는 핵심 인프라 객체**이다.
- SQLModel의 `Session`은 내부적으로 SQLAlchemy의 `Session` 아키텍처를 그대로 상속받아 동작한다.

## 동작 과정 및 쿼리 전송 메커니즘 (Flush vs Commit)

세션 내부에서 SQL 쿼리가 생성되어 데이터베이스 서버로 실제 전송되는 시점은 단순 커밋 순간이 아니며, **영속성 컨텍스트의 생명주기**에 따라 정밀하게 움직인다.

```
[객체 추가] ➔ session.add(user_model) # 메모리 상에서 상태 추적 시작 (SQL 발행 안 됨)  
│  
▼  
[쓰기 지연 및 전송] ➔ session.flush() 또는 자동 autoflush 유발 시점  
│ # 💡 이 지점에서 실제 INSERT / UPDATE 같은 Raw SQL이 생성되어 DB로 송신됨  
▼  
[트랜잭션 확정] ➔ session.commit()  
# 데이터베이스 서버에 반영된 변경 사항을 최종 원자적 확정 (트랜잭션 완결)
```
1. **객체 등록 (`add`):** 
	- `table=True` 설정을 통해 DB 테이블 스펙과 매핑된 SQLModel 인스턴스를 세션에 등록한다. 이 시점에는 메모리 상에서 상태 변경만 추적할 뿐, DB로 쿼리를 날리지 않는다. 
2. **쓰기 지연 및 데이터 전송 (`flush`):** 
	- 메모리에 쌓인 변경 내역을 바탕으로 실제 SQL 쿼리를 빌드하여 데이터베이스 서버로 밀어 넣는 단계를 **`Flush`**라고 한다. 
	- **⚠️ [실무 핵심] Autoflush의 진실:** 
		- 개발자가 직접 `session.flush()`를 치지 않더라도, SQLModel은 기본적으로 `autoflush=True` 스펙이 가동된다. 따라서 데이터를 추가한 뒤 **하단에서 새로운 조회(`select`) 명령을 내리는 순간**, 데이터 정합성을 맞추기 위해 세션이 알아서 `flush`를 발생시켜 쿼리를 DB로 전송한다. 
3. **최종 확정 (`commit`):** 
	- `flush`를 통해 DB 서버의 임시 트랜잭션 공간에 이미 들어가 있는 데이터 변경 사항들을 최종적으로 디스크에 반영하도록 승인(`commit`)하고 소켓 연결 스코프를 안전하게 닫는다.

## 커넥션 풀(Connection Pool)의 관리 주체와 구조적 분리 

아키텍처에서 인프라 자원을 효율적으로 분배하기 위해 세션과 풀의 책임을 명확히 격리한다. 

- **`Engine` 객체의 중앙 집중 관리 (커넥션 풀의 주인):** 
	- 데이터베이스와의 물리적 연결 통로들의 묶음인 커넥션 풀은 **`Engine` 인스턴스가 전역에서 독점적으로 생성하고 관리**한다. FastAPI 프레임워크나 자생적 UnitOfWork 디자인 패턴이 커넥션 풀을 직접 쪼개거나 생성하지 않는다. 
- **`Session` 객체의 자원 대여:** 
	- 세션이 오픈될 때, 세션은 전역 `Engine`이 관리하는 단일 커넥션 풀에서 **단 '1개'의 빈 커넥션을 대여(Checkout)** 받아 자신의 비즈니스 스코프 동안 전점 사용한다. 연산이 완료되어 세션이 닫히면(`close`), 대여했던 커넥션은 끊어지지 않고 다시 `Engine`의 커넥션 풀로 안전하게 반납(Return)된다. 
### 💡 UnitOfWork(UoW) 패턴을 따로 구현하는 진짜 이유 
- 수동으로 UoW를 설계하는 이유는 커넥션 풀의 분리를 막기 위해서가 아니다. 
- 비즈니스 레이어에서 여러 개의 리포지토리(`UserRepository`, `OrderRepository` 등)를 호출할 때, 각 리포지토리가 풀에서 커넥션을 각자 따로 빌려와 각자 트랜잭션을 터뜨리는 파편화를 막기 위함이다. 
- UoW라는 컨텍스트 매니저 방어벽을 정면에 세움으로써, **"하위의 모든 레포지토리들이 단 '1개'의 동일한 세션 인스턴스(동일한 커넥션)를 공유하여 완벽한 단일 트랜잭션 원자성"**을 유지하도록 조율하는 것이 패턴의 본질적 목표이다. 
## 프로젝트에서는 어디에서 사용하는가? 
- **레포지토리 주입:** 
	- 모든 구체 데이터베이스 제어 로직을 전담하는 `Infrastructure Layer` 내부의 데이터 레포지토리 계층에서 쿼리를 생성하고 수행하는 중추 코어로 사용된다. 
- **UoW 결합:** 
	- 어플리케이션 서비스 계층 영역에서는 데이터베이스 세션을 직접 노출하지 않고, `with...yield` 라이프사이클로 관리되는 **`UnitOfWork` 컨텍스트의 내부 주입 매커니즘**을 통해서만 세션의 생명주기를 안전하게 구동하고 제어하고 있다.
