## 왜 필요한가?  

> 기존 데이터베이스(RDBMS, NoSQL)는 매초 수만 건씩 쏟아지는 시계열 데이터를 감당할 수 없다.

- **[폭발적인 데이터 쓰기(write) 속도]**
	- [문제점:]
		- 관계형 DB는 데이터가 들어올 때마다 정렬, 인덱스 수정, 중복 체크(PK)를 하느라 속도가 점점 느려진다.
	- [TSDB 해결책:]
		- **오직 시간 순서대로 추가(Append-only)** 하는 것에만 집중해, 초당 수십만건의 대규모 데이터도 지연 없이 실시간으로 저장한다.
- **[저장 공간의 혁신적인 절약 (데이터 압축)]**
	- [문제점:]
		- 1초마다 센서 데이터가 쌓이면 한 달 만에 수십 억 건의 데이터가 쌓여 디스크가 마비된다.
	- [TSDB 해결책:]
		- 시계열 데이터는 앞뒤 데이터의 형태가 비슷하다는 특성이 있다.
		- 이를 이용한 특수 압축 알고리즘을 사용해 **일반 DB 대비 저장 공간을 최대 90% 이상 절약**한다.
- **['시간 범위' 조회 및 집계의 초고속화]**
	- [문제점:]
		- 일반 DB에서 "최근 3개월간 전체 장비의 시간별 평균 온도 구하기"를 실행하면 수억 건의 행을 처음부터 끝까지 읽어야 해서 몇 분 이상 걸리거나 서버가 멈춘다.
	- [TSDB 해결책:]
		- 데이터가 이미 시간순으로 정렬되어 있어, 특정 시간 범위를 지정한 **평균, 최댓값, 최솟값 등의 통계 연산을 단 수 밀리초(ms) 만에** 끝낸다.
- **[자동 데이터 관리 (용량 최적화)]**
	- [문제점:]
		- 오래된 로그나 센서 데이터를 수동으로 지우는 작업은 일반 DB에서 매우 무거운 작업(DELETE)이며 성능을 떨어뜨린다.
	- [TSDB 해결책:]
		- "30일이 지난 데이터는 자동으로 삭제"하거나 "1초 단위 데이터를 1분 단위 평균값으로 압축(Downsampling)하고 원본은 삭제"하는 정책을 알아서 수행한다.

## 정의  

> 시간(timestamp)과 그에 따른 값(value)이 한 쌍을 이루는 **[시계열 데이터를 빠르게 저장하고 조회하도록 최적화된 특수 목적의 데이터베이스]**다.

## 특징

- **[고속 쓰기 및 압축]**
	- 동시다발적으로 들어오는 방대한 양의 데이터를 지연없이 기록해, 저장공간을 효율적으로 아끼기 위해 압출륙이 높다.
- **[시간 기반 집계 및 분석]**
	- 특정 시간 범위의 평균, 최댓값, 추세등을 아주 빠르게 계산한다.
- **[데이터 보존 정책]**
	- 오래된 데이터를 자동으로 지우거나 요약하는 기능을 제공해, 디스크 용량 관리에 용이하다.

## 대표적인 TSDB 종류

- **Prometheus:** 서버 및 컨테이너 모니터링/알람에 널리 쓰이는 오픈소스 TSDB
- **InfluxDB:** 시계열 데이터 처리에 특화되어 시각화 도구와 연동이 쉬운 오픈소스 DB
- **TimescaleDB:** 관계형 데이터베이스인 PostgreSQL 기반 위에 시계열 기능을 얹은 확장형 DB

## 주요 활용 분야

- **인프라 및 서버 모니터링:** CPU 사용량, 메모리, 네트워크 트래픽 등 실시간 시스템 상태 측정
- **사물인터넷(IoT):** 스마트팩토리 센서, 스마트홈 기기, 차량 운행 기록 등에서 발생하는 수많은 상태값 수집
- **금융 및 주식:** 실시간 주가 변동, 거래 내역, 가상화폐 시세 기록 및 분석

## 동작 과정  

> 대부분의 현대적인 TSDB는 LSM-Tree(**Log-Structured Merge-Tree) 변형 구조**나 **시계열 전용 스토리지 엔진**을 사용하여 다음과 같은 4단계 과정을 거쳐 동작한다.

```
1. 데이터 수집 및 수신
   - 데이터가 수집기(Telegraf, Prometheus Exporter 등)를 통해 TSDB로 들어오는 단계다.
2. 시간 단위 블록 분할 및 압축
   - 메모리 버퍼에 데이터가 일정량 쌓이거나 특정 시간이 지나면, 디스크의 불변 스토리지 블록으로 변환하여 저장한다.
3. 인덱싱을 통한 초고속 조회
   - 사용자가 쿼리를 요청했을 때의 동작이다.
1. 백그라운드 최적화
   - 시스템이 쉬는 동안 지속적으로 데이터 저장 상태를 최적화 한다.
```

### 1. 데이터 수집 및 수신 (Ingestion)

- 데이터가 수집기(Telegraf, Prometheus Exporter 등)를 통해 TSDB로 들어오는 단계다.

### 2. 시간 단위 블록 분할 및 압축 (Storage & Compression)

- 메모리 버퍼에 데이터가 일정량 쌓이거나 특정 시간이 지나면, 디스크의 불변 스토리지 블록으로 변환하여 저장한다.

### 3. 인덱싱을 통한 초고속 조회 (Querying)

- 사용자가 쿼리를 요청했을 때의 동작이다.

### 4. 백그라운드 최적화 (Compaction & Retention)

- 시스템이 쉬는 동안 지속적으로 데이터 저장 상태를 최적화 한다.

## RDB와 TSDB의 차이

### 1. B-Tree는 [정렬]을 유지해야 한다. (페이지 분할 문제)

>B-Tree는 데이터가 항상 완벽하게 정렬된 상태를 유지하는 자료구조다.

- [네트워크 지연과 데이터 역전]
	- 현실에서는 네트워크 지연때문에 1초전 데이터가 지금 도착하는 일(Out-of-order)이 빈번한다.
- [RDB (B-Tree)의 경우]
		- 아주 살짝만 과거의 데이터가 들어와도 B-Tree는 정렬을 유지하기 위해 이미 꽉 찬 디스크 블록(Page) 사이에 공간을 만드려고 페이지 분할(Page split)을 일으킨다.
		- 이 과정에서 막대한 IO와 Lock이 발생하여 자원이 소모된다.
- [TSDB (LSM-Tree 등)의 경우]
		- TSDB는 주로 LSM-Tree 기반의 구조를 쓴다.
		- 데이터가 들어오면 정렬은 신경쓰지 않고 일단 메모리에 순서대로 적재한다.
		- 나중에 메모리가 차면 디스크에 동째로 순차 기록(Flush)하고, 멈춤 없이 백그라운드에서 조용히 정렬(Merge)한다.
### 2. 고차원 인덱스(ID/TAG)의 유무

> 현실의 시계열 데이터는 '시간'뿐만이 아닌, 어떤 장비(ID)의, 어떤 위치(TAG)에서 온 데이터인지가 함께 들어온다.

- [RDB (B-Tree)의 경우]
	- 시간순으로 정렬하더라도, 특정 장비의 데이터만 뽑으려면 (장비ID, 시간) 조합으로 복합 인덱스를 걸어야 한다. 
	- 이 순간 순수한 시간순 입력이 깨진다. 
	- 장비 ID가 수만 개라면 B-Tree의 여기저기 사방에 데이터가 흩어져 저장되므로 심각한 랜덤 I/O가 발생한다.
- [TSDB (LSM-Tree 등)의 경우]
	- 시간(Time)과 메타데이터(Tag)를 완전히 분리한다.
	- 장비 ID 같은 태그는 별도의 문자열 인덱스(Inverted Index)로 관리하고, 실제 수치 데이터는 오직 시간 축 하나로만 묶어서 일렬로 저장한다.

### 3. 저장 방식의 차이 (행 기반 vs 열 기반)

> B-Tree를 쓰는 일반 RDB는 대개 행(Row) 기반 저장 방식이다.

- [RDB (B-Tree)의 경우]
	- 데이터 한 줄(시간, 장비ID, 온도, 습도, 전압)이 디스크에 통째로 붙어서 저장된다. 
	- 만약 1억 건의 데이터에서 '1달간 평균 온도'만 구하고 싶어도, 필요 없는 습도, 전압, 장비 ID까지 디스크에서 전부 읽어와야(Full Table Scan) 하므로 I/O 병목이 생긴다.
- [TSDB (LSM-Tree 등)의 경우]
	- 열(Column) 기반 저장 방식이 많다. 
	- '온도' 데이터만 디스크 한곳에 모아서 저장합니다. 
	- 1억 건의 온도 평균을 구할 때 딱 온도 컬럼만 초고속으로 읽어 들이기 때문에 집계 속도가 비교가 안 될 정도로 빠르다.

### 4. 압축 알고리즘의 유무

> 시계열 수치 데이터는 바로 앞 데이터와 값이 비슷할 확률이 매우 높습니다. 
> (e.g: 25.1도 -> 25.2도 -> 25.2도)

- [RDB (B-Tree)의 경우]
	- 일반적인 B-Tree 블록 압축은 이런 수치적 특성을 활용하지 못해 압축률이 떨어지고 데이터 덩치가 크다.
- [TSDB (LSM-Tree 등)의 경우]
	- 이 특성을 이용해 Gorilla 압축이나 Delta-of-Delta 같은 시계열 전용 압축 알고리즘을 쓴다. 
	- 정수나 실수의 차이점(변화량)만 기록하여 데이터를 최대 90% 이상 압축한다. 
	- 디스크에 적을 용량 자체가 10분의 1로 줄어드니 쓰기 속도도 그만큼 빨라진다.
