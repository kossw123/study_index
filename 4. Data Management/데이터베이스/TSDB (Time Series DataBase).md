## 왜 필요할까?

- **시계열 데이터의 폭발적인 처리:** 
	- IoT 센서, 인프라 메트릭 등 매초 수만 건 이상 대규모로 쏟아지는 시계열 데이터를 RDBMS나 일반 NoSQL로 처리할 경우, 인덱스 유지 및 트랜잭션 오버헤드로 인해 시스템 자원 대비 비용 효율성이 급격히 저하된다.
- **스리지 공간의 임계치 방어:** 
	- 동일한 형태의 데이터가 무한히 누적되는 시계열 특성상, 일반적인 블록 압축 기술로는 수십억 건의 디스크 용량 포화를 감당하기 어렵다.
- **대규모 통계 연산의 최적화:** 
	- "최근 수개월간 특정 장비의 시간별 데이터 추이 분석"과 같은 대량의 시간 범위 집계 쿼리를 수행할 때 발생하는 디스크 I/O 병목을 제거하기 위해 탄생했다.

## 정의

- **TSDB (Time Series Database, 시계열 데이터베이스)**는 시간(Timestamp)과 그에 따른 수치값(Value)이 연속적으로 매핑되는 **시계열 데이터를 고속으로 기록(Ingestion)하고, 특정 시간 범위를 기준으로 빠르게 조회/집계할 수 있도록 스토리지 엔진이 특화된 목적형 데이터베이스**이다.

## RDB 아키텍처와의 구조적 차이점 분석

### 1. 쓰기 모델의 차이: B-Tree vs LSM-Tree 아키텍처
- **RDBMS (B-Tree 계열):** 
	- 데이터의 실시간 정렬 상태를 유지하기 위해 디스크 페이지 구조를 엄격히 관리한다. 
	- 만약 네트워크 지연 등으로 과거 데이터(Out-of-order)가 뒤늦게 유입될 때, 해당 디스크 블록(Page)이 이미 100% 가득 차 있다면 데이터 공간 확보를 위해 무거운 **페이지 분할(Page Split)**과 Lock을 유발하여 쓰기 성능 저하를 야기할 수 있다.
- **TSDB (주로 LSM-Tree 변형 엔진):** 
	- 데이터 유입 시 디스크로 직행하지 않고, 메모리 내의 버퍼(**MemTable**) 영역에서 1차적으로 정렬 구조(Skip List 등)를 유지하며 쓰기 요청을 빠르게 흡수한다. 
	- 버퍼가 가득 차면 디스크에 순차 파일(SSTable) 형태로 한 번에 밀어내고(Flush), 정렬과 병합은 백그라운드 스레드(`Compaction`)에 전담시켜 사용자의 쓰기 지연을 최소화한다. 
	- (※ 단, Prometheus처럼 자체적인 고유 시계열 블록 엔진을 쓰는 독립 제품군도 존재한다.)

### 2. 데이터 저장 패러다임: 행(Row) 기반 vs 열(Column) 기반
- **RDBMS (행 기반):** 
	- 한 줄의 레코드(시간, 장비ID, 온도, 습도)가 디스크의 인접한 블록에 통째로 묶여 저장된다. 수억 건의 데이터 중 오직 '온도 평균'만 구하고 싶을 때, 적절한 커버링 인덱스가 설계되어 있지 않다면 필요 없는 습도 데이터까지 디스크에서 읽어 들이는 구조적 I/O 비효율이 발생한다.
- **TSDB (주로 열 기반):** 
	- 각 지표(Metric)별 수치 데이터를 컬럼 단위로 디스크에 분리 저장한다. '온도' 집계 시 오직 온도 데이터 컬럼만 정밀하게 스캔하므로 전체 행을 스캔할 필요가 없어 데이터 레이어의 읽기 성능이 비약적으로 향상된다.

### 3. 고차원 인덱스 제어 (High Cardinality 대응)
- 시계열 데이터는 '시간' 외에도 어떤 서버 호스트(`host`), 어떤 서비스 환경(`env`)에서 온 메트릭인지 식별하는 태그(Tag/Label) 데이터가 결합된다.
- TSDB는 수많은 태그 조합으로 인해 인덱스 크기가 폭발하는 현상(High Cardinality)을 방어하기 위해, **태그 정보는 역색인(Inverted Index) 구조로 메타데이터화하여 관리하고 실제 수치 데이터는 순수한 시간 축으로만 묶어 관리**하는 이원화 아키텍처를 취한다.

### 4. 시계열 전용 압축 알고리즘 탑재
- 시계열 수치 데이터는 직전 데이터와 값이 매우 유사하거나 소수점 변화만 일어나는 특성(예: 24.1 ➔ 24.1 ➔ 24.2)을 가진다.
- TSDB는 이 특성을 극대화한 **Gorilla 압축**이나 **Delta-of-Delta** 알고리즘을 사용하여 정수/실수의 변화량(차이값)만 비트 단위로 조밀하게 가공한다. 이를 통해 스토리지 공간을 최대 90% 이상 절약하여 비용을 절감한다. (※ 단, 압축 과정에서 CPU 연산 자원이 추가 소모되므로 인프라 환경별 프로파일링이 수반된다.)

## 동작 과정 (데이터 수명 주기 관리)

```
[지표 수집] ➔ [메모리 버퍼 적재] ➔ [시간 단위 불변 블록 생성] ➔ [백그라운드 최적화 및 롤업]
```

1. **지표 수집 및 수신 (Ingestion):** 
	- 수집기(Prometheus Exporter, Telegraf 등)가 밀어주거나 TSDB가 풀링(Pulling)하여 시계열 데이터를 수신한다. 
2. **청크 및 블록 분할 (Storage):** 
	-  메모리 버퍼에서 일정 시간(예: 2시간 단위) 동안 데이터를 보관 및 정렬한 뒤, 디스크에 수정이 불가능한 불변(Immutable) 시계열 블록 파일로 내려쓴다. 
3. **데이터 보존 정책 자동화 (Retention & Downsampling):** 
	-  오래된 원본 시계열 로그를 수동으로 `DELETE`하면 DB 성능이 마비되므로, TSDB는 내장 정책에 따라 오래된 데이터를 자동 삭제한다. 더불어 1초 단위 데이터를 5분 단위 평균값으로 요약 변환하고 원본은 소멸시키는 **다운샘플링(Downsampling)** 파이프라인을 자체 구동하여 디스크 용량을 최적화한다. 
## 프로젝트에서는 어디에서 사용하는가? 
- **오픈소스 가시성 스택 (LGTM) 연동:** 
	- 우리 시스템의 모니터링 아키텍처인 LGTM 인프라 구조 중, 시스템의 메트릭 정보를 수집하고 알람을 트리거하는 중추 레이어로 **Prometheus(TSDB)**를 도입하여 활용 중이다. 
- **인프라 모니터링:** 
	- 시스템 내부에서 발생하는 CPU, 메모리 가동률, FastAPI 엔진의 엔드포인트별 응답 가용성 시간 데이터를 초 단위로 파이프라인화하여 Prometheus에 기록하고 이를 Grafana 대시보드로 시각화하여 관찰하고 있다.
