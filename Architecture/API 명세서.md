## 왜 필요한가?

- 간단하게 개발자 간의 의사소통 비용을 0에 가깝게 줄일 수 있다.
- 의사소통 비용이 적어져서 시스템 구축 속도를 획기적으로 높일 수 있다.

## 정의

- 서로 다른 프로그램이 데이터를 주고받을 때 필요한 요청 방식, 데이터 형식, 응답 규격을 상세히 기록한 표준화된 설명서

> 필수적으로 3대 정의를 서술해야 한다.
> 1. 상호 작용의 규약
> 	1. 어떤 주소와 HTTP method로 데이터를 보내야 하는지
> 	2. 서버는 어떤 형태로 응답을 돌려줄 것인지
> 2. 구조적 명세화
> 	1. 매개변수의 이름, 타입, 필수 여부, HTTP 상태 코드 등을 구조화된 형식으로 제작
> 3. 독립적 문서화
> 	1. IDE 환경, 언어 상관없이, Web이라는 공통 공간의 HTTP라는 규격화된 틀 안에서 보고 즉시, 통신 코드를 알 수 있도록 중립적인 형태로 표현해야 한다.
> 		1. 중립 적인 형태란, 주로 JSON이나, YAML, Swagger 웹 화면 등을 의미한다.


## REST API와 차이점

> API 명세서는 프론트엔드, 백엔드 개발자가 협업하기 위해 작성하는 [데이터 교환 양식]이다.
> 간단하게 말해서 REST API는 [건축 양식], API 명세서는 [설계도(문서)]이라고 할 수 있다.
> API 명세서가 더 구체적이다.

보통 API 명세서를 볼 때 다음과 같은 요소를 중점으로 본다.

1. 기능 명칭
	- 이 API가 무슨 일을 하는가?(e.g: 로그인, 상품 검색 등 )
2. HTTP method 및 URI
	- 어떤 주소로, 어떤 방식으로 요청해야 하는가?(e.g: `POST v1/auth/login`)
3. 요청 매개변수
	- 클라이언트에서 서버로 보낼 때 첨부해야 하는 데이터 목록과 자료형
4. 응답 데이터
	- 성공 했을 때 서버가 돌려주는 JSON 데이터 구조
5. 에러 코드
	- 실패 했을 때 반환되는 오류 메시지


## e.g

- 🔐 [POST] `/v1/auth/login` (로그인 요청)

```
**기능:** 이메일과 비밀번호를 받아 회원 인증을 진행하고 토큰을 발급합니다.
**요청 바디 (JSON):**

# json
{
  "email": "user@example.com",  // (필수) 가입된 이메일 주소
  "password": "password123!"     // (필수) 비밀번호 (8자 이상)
}
```

- **성공 응답 (200 OK):**

```
# json
{
  "success": true,
  "userName": "김철수",
  "accessToken": "eyJhbGciOiJIUzI1NiIsIn..."
}
```

- **실패 응답 (400 Bad Request - 비밀번호 불일치):**

```
# json
{
  "success": false,
  "errorCode": "AUTH_001",
  "message": "비밀번호가 일치하지 않습니다."
}
```
