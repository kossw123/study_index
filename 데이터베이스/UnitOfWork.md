
## 왜 필요한가?  

- DDD 패턴이 기반된, Application, Infra Layer 사이 적절한 trade-off가 필요하여 작성되었다.
- WAS와 DB 사이 통신 성능 저하를 해결하기 위해 UnitOfWork를 사용한다.
## 정의  

비즈니스 로직과 DB 사이에서 트랜잭션을 관리하는 디자인 패턴이다.

## 동작 과정  

벌크 연산과 비슷하게 움직이지만 엄연하게 다른 과정을 가진다.

“하나의 비즈니스 로직을 위해 발생되는 ‘서로 다른 종류의 작업들’을 하나의 트랜잭션으로 묶어주기만 한다”

그러나 벌크 연산은 하나의 테이블에 똑같은 형태의 데이터를 수천, 수만건 넣을 때, SQL 문법 자체를 한 줄로 합쳐서 한 방에 실행하는 기술이다.

즉, 벌크 연산은 쿼리의 양을 기술적으로 압축하는 “스킬”

UOW는 비즈니스 로직 과정을 안전하게 감싸주는 “컨테이너”라고 이해하면 좋다.
  
## 프로젝트에서는 어디에서 사용하는가?  

- Application, Infra Layer 사이에서 전반적으로 활용된다.


## WAS와 DB사이 통신 중 성능 저하 요소

단순하게 생각해보면 DB Query는 자주 사용하면 할수록 성능 저하가 생긴다.

왜냐하면 다음과 같은 비용이 소모되기 때문이다.

1. 네트워크 왕복 비용(Network Round Trip Time, RTT)
	- 반복문을 통해 여러 쿼리를 한번에 보낸다고 해보자.
	- 그러면 쿼리를 하나 보내는데 5ms가 걸린다하면 5 * n의 소비가 발생된다.
	- 이를 백엔드에서 N+1 문제 또는 채티(chatty) API라 부른다.
2. 쿼리를 계산하는 DB 서버의 CPU/메모리 과부하(Parsing & Execution Plan)
	- DB 서버는 쿼리가 들어올 때마다 다음과 같은 계산을 한다.
	- 구문 분석
	- 최적화
	- 잠금
	- 결국 이 과정을 쿼리가 하나 들어올 때마다 계산하고, 이게 100개가 들어오면 엄청난 계산 비용이 든다.
3. Connection Pool 고갈 문제
	- FastAPI와 DB 서버는 미리 통로(conntection)을 몇개 뚫어놓고 돌려쓴다.
	- 왜냐하면 매번 요청할때마다 연결하고 끊는 작업은 비용이 많이 들기 때문이다.
	- 각기 다른 쿼리가 50개가 동시에 들어온다면 Connection Pool은 20개가 사용되고 나머지 30개는 기다리게 되며, 결과적으로 다른 모든 사용자의 서비스까지 지연된다.
4. I/O 병목
	- 메모리는 엄청 빠르지만, 결국 영구 저장을 위해 SSD/HDD에 저장할 수밖에 없다.
	- 그리고 INSERT, UPDATE, DELETE 같은 쿼리가 많아지면, 어찌됐든 메모리에 저장된 데이터에 접근하는 비용이 발생하게 된다.

## 다른 해결 방법

1. 벌크 연산 : 100번 쿼리를 보낼걸 한번에 모아서 보낸다.
	- 보통 쿼리 한번은 다음과 같이 선언하면
		INSERT INTO users (name) VALUES ('kim");
	- 벌크 연산은 다음과 같이 선언된다.
		INSERT INTO users (name) VALUES ('kim'), ('lee'), ...;
2. 조인 및 Eager Loading : 여러 테이블 데이터를 찢어서 여러 번 조회하지 않고 한 번에 엮어서 1개의 쿼리로 만든다.
3. 캐싱(Caching) : 자주 조회되며, 잘 변하지 않는 데이터는 DB가 아닌 메모리 기반 저장소(Redis)에 올려두고 더 빠르게 가져온다.
4. UnitOfWork: 서로 다른 작업을 하나의 트랜잭션으로 묶어서 처리한다.

보통 UnitOfWork와 벌크 연산을 합쳐서 사용한다.
