## 왜 필요할까?

- **웹 표준(HTTP) 인프라의 레버리지:** 전 세계 인터넷망의 표준 규격인 HTTP 프로토콜을 그대로 활용하므로, 별도의 무거운 통신 라이브러리나 복잡한 설정 없이도 서로 다른 플랫폼(언어, 프레임워크)으로 구축된 시스템 간에 유연하게 데이터를 송수신할 수 있다.
- **클라이언트와 서버의 독자적 진화:** 서버와 클라이언트가 주고받는 리소스 인터페이스 규칙만 유지된다면, 서버의 내부 비즈니스 로직이나 DB 구조가 통째로 바뀌더라도 클라이언트 코드를 수정할 필요가 없어 시스템 간 결합도가 대폭 낮아진다.

## 정의

- **REST (Representational State Transfer)**는 2000년 로이 필딩(Roy Fielding)의 박사학위 논문에서 최초로 제안된 아키텍처 스타일로, **웹의 원천 인프라 기술인 HTTP 프로토콜의 강점(무상태성, 캐시 가능성, 유니폼 인터페이스 등)을 극대화하여 분산 하이퍼미디어 시스템을 설계하기 위한 가이드라인 체계**이다.
- 이 규칙을 충족하도록 설계된 API를 **RESTful API**라고 부른다.

## 핵심 제약 조건에 대한 기술적 오해 교정

### 1. HATEOAS와 데이터 포맷의 본질
- REST 아키텍처는 JSON 형식을 강제하거나 `_links`라는 특정 필드명을 필수로 요구하지 않는다. 본질은 **HATEOAS(애플리케이션 상태의 엔진으로서의 하이퍼미디어)** 제약 조건으로, 서버의 응답 내에 다음 행동을 취할 수 있는 URL 링크를 동적으로 포함하여 제공해야 한다는 원칙이다.
- 응답 내에 단순히 하이퍼링크를 포함시켰다고 해서 REST 아키텍처 스타일을 완벽히 충족하는 것은 아니다. 메시지 자체가 스스로의 처리 방법을 온전히 설명할 수 있어야 하는 **Self-descriptive messages(미디어 타입 표준 명시 등)** 등의 까다로운 제약 조건을 모두 충족해야 진정한 의미의 로이 필딩식 REST API가 완성된다.

### 2. 클라이언트-서버 간 보안 제어 책임의 명확화
- **⚠️ [보안 필수]** 사용자의 잔액 고갈이나 계좌 정지 상태에 따라 서버가 응답에서 `_links.withdraw(출금)` 엔드포인트를 누락시켜 프론트엔드 UI를 제어하는 방식은 가독성을 돕는 수단일 뿐이다.
- 공격자가 기존에 발급받았던 출금 URI 주소로 직접 HTTP 패킷을 강제 위조하여 유입시킬 수 있으므로, **API 주소를 숨기는 행위와 무관하게 서버 측 백엔드 비즈니스 도메인 계층에서의 상태 검증 및 인가(Authorization) 가드 로직은 무조건 완벽하게 가동**되어야 한다.

## 현대 실무의 웹 API 설계 패러다임 (Pragmatical REST)

현대 엔터프라이즈 환경에서는 로이 필딩의 순수 REST 제약 조건을 엄격하게 모두 따르기보다, **HTTP 메서드의 의미론적 강점과 리소스 중심의 URI 규칙을 차용하여 실용적으로 설계하는 'HTTP API' 스타일**을 널리 준수한다.

### 💡 리소스(Resource) 중심 명사형 URI 라우팅 스펙

| 주요 기능 | HTTP 메서드 (행위) | 구조적 URI (대상 리소스) | 아키텍처 스펙 및 특징 |
| :--- | :--- | :--- | :--- |
| **결제 요청 생성** | `POST` | `/v1/payments` | 새로운 결제 '자원(Resource)'을 서버에 생성한다. (URI에 `create_payment` 같은 동사형 표현을 쓰지 않는 것이 원칙이다.) |
| **결제 상세 조회** | `GET` | `/v1/payments/pay_8842` | 고유 식별자(`pay_8842`)를 가진 특정 결제 자원의 상태 데이터를 안전하게 가져온다. (조회 메서드는 멱등성을 지닌다.) |
| **결제 취소 처리** | `POST` | `/v1/payments/pay_8842/cancels` | **⚠️ [도메인 교정]** 결제 취소는 기존 자원을 디스크에서 완전 삭제하는 행위가 아니므로 **`DELETE`를 쓰지 않는다.** 결제를 거듭 취소하여 부분 취소 자원들을 하위로 누적 생성하거나, 취소라는 상태 전이 행위를 일으키는 성격이므로 **`POST` 문맥으로 하위 자원을 생성하도록 설계**하는 것이 완벽한 비즈니스 명세 방식이다. |

## 통신 흐름 예시 (이해를 돕기 위한 가상 시나리오)

> ※ 본 메시지 블록은 실제 토스페이먼츠 상용 API 계약서 스펙과 무관한, REST 아키텍처 설계 이해를 돕기 위한 가상의 명세서 예제입니다.

### 1. Client의 HTTP Request (결제 상세 조회 데이터 요청)
```http
GET /v1/payments/pay_8842 HTTP/1.1
Host: api.virtual-gateway.net
Authorization: Bearer secret_live_key_9999
Accept: application/json
```

### 2. Server의 HTTP Response (정제된 데이터 반환)
```json
{
  "paymentId": "pay_8842",
  "orderName": "맥북 에어 M3",
  "amount": 1590000,
  "status": "DONE",
  "approvedAt": "2026-07-16T15:30:00"
}
```

## 프로젝트에서는 어디에서 사용하는가?

- **분산 시스템 자원 통신 규격:** 프론트엔드 컴포넌트와 백엔드(FastAPI) 프레임워크가 물리적 경계를 넘어 교차 출처 간 데이터를 안정적으로 송수신할 수 있도록, **명사 중심의 리소스 구조와 HTTP 표준 상태 코드를 전면 채택한 실용적 RESTful 웹 API 구조**로 어플리케이션 인터페이스를 설계하여 운영 중이다.
