## 왜 필요할까?

- **팀 간 오해 및 소통 비용의 획기적 단축:** 프론트엔드와 백엔드 개발자, 혹은 사내 시스템 간의 데이터 교환 규격을 서면으로 명확히 합의함으로써, 구현 단계에서 발생하는 스펙 조율 비용과 커뮤니케이션 오버헤드를 최소화한다.
- **병렬 개발 환경 구축을 통한 속도 향상:** 명세서가 정립되면 프론트엔드 개발자는 백엔드 구현이 완전히 끝나지 않더라도, 명세된 응답 규격을 기반으로 가짜 데이터(Mock Data)를 만들어 화면 개발을 즉시 진행할 수 있어 전체 시스템 구축 속도가 빨라진다.

## 정의

- **HTTP API 명세서 (Web API Specification)**는 서로 다른 프로그램(클라이언트와 서버 등)이 웹 브라우저/네트워크 환경에서 데이터를 주고받을 때 필요한 **진입 주소, 데이터 요청 포맷, 성공 및 실패 응답 규격을 상세히 기록한 표준 기술 문서**이다.

### 🏗️ 좋은 HTTP API 명세서가 갖추어야 할 3대 속성
1. **상호 작용의 명확한 규약:** 어떤 엔드포인트(URI)와 HTTP 메서드(GET, POST 등)를 조합하여 데이터를 전송해야 안전하게 도달하는지 정의한다.
2. **구조적 스키마 명세화:** 유입되는 매개변수의 키 이름, 자료형(Type), 필수 값 여부, 성공/실패 시의 HTTP 상태 코드들을 구조화된 포맷으로 정의한다.
3. **플랫폼 독립적 문서화:** 특정 프로그래밍 언어나 개발 도구에 종속되지 않고, 웹 표준 환경에서 누구나 즉시 이해할 수 있도록 중립적인 형태(주로 OpenAPI 스펙 기반의 Swagger UI, Postman, 또는 JSON/YAML 문서)로 표현된다.

## 아키텍처 관점의 차이: REST API vs API 명세서

- **REST API (Architectural Style):** 자원 중심의 웹 표준 설계를 지향하는 **'건축 철학 / 설계 양식'**이다.
- **API 명세서 (Specification Document):** 그 양식을 기반으로 특정 비즈니스 유스케이스(예: 로그인, 결제 등)를 처리하기 위해 구체적인 데이터 스펙을 한 땀 한 땀 기록해 둔 **'실물 설계도면'**이다. 명세서가 훨씬 구체적이고 실무적이다.

## HTTP API 명세서 예시 (설명용 가이드라인)

> ⚠️ **[문법 주의]** 본 예시 내의 데이터 블록은 가독성을 높이기 위해 주석 기호(`//`)를 첨부한 **'설명용 가이드 텍스트'**입니다. **표준 JSON 명세(RFC 8259)는 주석을 일절 허용하지 않으므로**, 실제 백엔드/프론트엔드 코드나 통신 패킷에 그대로 주석을 포함하여 전송하면 구문 분석 에러(`JSONDecodeError`)가 발생합니다.

🔐 **[POST]** `/v1/auth/login` (로그인 요청)
- **기능 설명:** 사용자의 이메일과 비밀번호를 받아 회원 인증을 진행하고 보안 인증 토큰을 발급한다.

### 1. 요청 바디 명세 (Request Body)
```json
{
  "email": "user@example.com",  
  "password": "password123!"     
}
```
- `email` (string, 필수): 서비스에 가입된 이메일 계정 형식의 문자열
- `password` (string, 필수): 계정 비밀번호 (보안 강화를 위해 8자 이상 강제)

### 2. 비즈니스 성공 응답 (200 OK)
```json
{
  "success": true,
  "userName": "김철수",
  "accessToken": "eyJhbGciOiJIUzI1NiIsIn..."
}
```
- `success` (boolean): 요청 처리 성공 여부
- `userName` (string): 인증이 완료된 회원의 실명
- `accessToken` (string): 향후 인가(Authorization) 처리를 위해 헤더에 첨부할 JWT 인증 토큰

### 3. 비즈니스 실패 응답 예시 (400 Bad Request - 비밀번호 불일치)
```json
{
  "success": false,
  "errorCode": "AUTH_001",
  "message": "비밀번호가 일치하지 않습니다."
}
```
- `errorCode` (string): 에러 추적 및 프론트엔드 다국어 처리를 위한 사내 표준 예외 식별 코드
- `message` (string): 사용자 화면에 노출하거나 디버깅 시 확인할 예외 메시지

## 프로젝트에서는 어디에서 사용하는가?

- **FastAPI OpenAPI 스펙 자동 파싱:** 우리 백엔드 프로젝트에서는 Pydantic 모델과 라우터 데코레이터를 연동하여 별도의 수동 문서 수정을 배제하고, 코드가 수정될 때마다 실시간으로 동기화되는 **내장형 Swagger UI 명세 아키텍처**를 활용 중이다.
- **프론트엔드 협업 관문:** 완성된 Swagger UI 대시보드 링크를 프론트엔드 팀과 공유하여, 데이터 타입 미스매치로 인한 장애를 배포 전 단계에서 완벽하게 상호 차단하고 있다.
