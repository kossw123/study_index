## 왜 필요할까?

- **인프라 자원 및 속도 최적화:** 백엔드 데이터베이스가 한 번에 수만 건의 레코드를 메모리에 적재하고 정렬(`Sort`)할 때 발생하는 극심한 CPU/메모리 오버헤드를 제어한다.
- **네트워크 대역폭 포화 방지:** 수백 MB에 달하는 대용량 데이터 패킷이 하나의 HTTP 응답 스트림으로 전송될 때 발생하는 네트워크 지연(Latency)과 데이터 비용 낭비를 차단한다.
- **클라이언트 런타임 크래시 방지:** 모바일 앱이나 웹 브라우저의 DOM 트리 엔진이 감당할 수 있는 정보의 양을 제어하여, 메모리 부족(OOM)으로 인해 브라우저 렌더링이 중단되거나 멈추는 현상을 예방한다.

## 정의

- **페이징 (Pagination)**은 데이터베이스에 누적된 대량의 데이터 집합을 비즈니스 요구사항에 맞춰 일정 크기(Size)의 조각으로 세분화한 뒤, **클라이언트의 요청 흐름에 따라 순차적으로 분할하여 서빙하는 데이터 레이어 최적화 기술**이다.

## 페이징 아키텍처의 종류 및 실무적 한계

### 1. 오프셋 기반 페이징 (Offset-based Pagination)
- **메커니즘:** 데이터베이스의 `LIMIT`와 `OFFSET` 구문을 활용해 특정 행 번호부터 지정한 개수만큼 데이터를 건너뛰어 가져오는 방식이다. (예: `[1] [2] [3]` 구조의 전통적인 웹 페이지 게시판)
- **⚠️ [정합성 필수] 안정적인 `ORDER BY` 결합:** 관계형 데이터베이스 명세상, 고유한 정렬 기준(`ORDER BY`)이 누락된 `LIMIT/OFFSET` 쿼리는 결과의 순서를 보장하지 않는다. 데이터 정합성을 위해 반드시 **인덱스를 타는 명확한 정렬 기준과 고유 키(PK) 정렬이 수반**되어야 한다.
- **구조적 한계 (대용량 병목):** 뒤 페이지(`OFFSET 1000000`)로 갈수록, 데이터베이스 엔진은 앞선 100만 건의 데이터를 디스크에서 **전부 읽어와(Full Scan) 메모리에서 버린 후** 다음 지정 개수만 반환하므로 성능이 기하급수적으로 저하된다. 또한, 사용자가 1페이지를 보는 동안 새로운 데이터가 삽입되면 2페이지 이동 시 데이터가 중복 노출되는 페이지 밀림 현상이 발생한다.

### 2. 커서 기반 페이징 (Cursor-based / No-offset)
- **메커니즘:** 페이지 번호 대신 **"직전 페이지에서 마지막으로 조회한 고유 아이템의 값(Cursor)"**을 이정표로 두고, 그 커서보다 뒤에 위치한 데이터만 좁혀서 `WHERE` 절로 즉시 타겟팅하는 방식이다. (예: 인스타그램, 유튜브의 무한 스크롤 및 더보기 버튼)
- **⚠️ [인덱스 종속성]** 커서 기반 페이징이 무조건 성능 우위를 가지는 것은 아니다. 커서 지정을 위한 `WHERE` 조건절이 **데이터베이스 내부의 B-Tree 인덱스를 완벽히 타도록 정밀하게 설계되어야만 비로소 일정한 고속 성능을 보장**한다. 인덱스가 없다면 이 또한 풀 테이블 스캔을 유발한다.
- **⚠️ [동률 구분: Tie-breaking 키의 필수성]** 정렬 기준 컬럼(예: 생성일시, 좋아요 수 등)의 값이 중복될 수 있는 경우, 단순히 그 값만 커서로 두면 데이터 유실이나 중복 루프가 터진다. 이를 방지하기 위해 **"정렬 기준 컬럼과 고유 식별자(PK)를 함께 묶어 조건절을 분기하는 복합 커서(Composite Cursor) 설계"**가 강제된다.

## 아키텍처 처리 과정 및 카운트 쿼리 최적화
```
[클라이언트 요청] ➔ /api/posts?cursor=125&size=10 (쿼리 스트링 명세)  
                         │
                         ▼
[백엔드 인덱스 라우팅] ➔ WHERE id < 125 ORDER BY id DESC LIMIT 11 (Has Next 계산을 위해 +1 조회)  
                         │
                         ▼
[카운트 오버헤드 최적화] ➔ ⚠️ 대용량 커서 페이징 시 무거운 SELECT COUNT(*) 전체 조회를 전면 생략  
                         │
                         ▼
[최종 JSON 응답 포맷] ➔ { "data": [...10개], "nextCursor": 115, "hasNext": true }
```

1. **클라이언트 매개변수 전송:** 쿼리 스트링을 사용하여 서버가 인덱싱을 추적할 수 있도록 커서 지표를 넘긴다. (예: `/api/posts?cursor=125&size=10`) 
2. **백엔드 SQL 인덱스 빌드:** 서버는 전달받은 커서 값을 쿼리문의 고속 인덱스 스캔 조건으로 매핑한다. - *오프셋 공식: `OFFSET = (Page - 1) * size` (뒤로 갈수록 대용량 풀 스캔 위험)* - *커서 공식: `WHERE id < :cursor LIMIT :size + 1` (인덱스 서칭을 통한 다이렉트 접근)* 
3. **전체 건수(Total Count) 조회의 인프라적 최적화:** - 숫자로 페이지 번호를 다 나열해야 하는 오프셋 방식은 전체 페이지 계산을 위해 무거운 `COUNT(*)` 쿼리가 강제된다. 이는 대용량 테이블에서 심각한 병목을 유발한다. - 무한 스크롤 환경의 커서 방식은 전체 건수 조회가 필수가 아니다. 요청한 `size`보다 **단 1개 더 많은 데이터를 조회(`LIMIT size + 1`)하여 다음 페이지 존재 여부(`hasNext`)만 판단**하는 전략을 취해 DB 자원을 획기적으로 아낀다. 
4. **결과 직렬화 및 렌더링:** 가공된 데이터 리스트와 다음 이정표가 될 `nextCursor` 값을 JSON으로 변환하여 프론트엔드로 송신하고 브라우저가 화면을 부분 동적 갱신한다. 
## 프로젝트에서는 어디에서 사용하는가? 
- **피드 및 로그 모니터링 아키텍처:** 우리 프로젝트의 대용량 타임라인 피드 및 Prometheus 지표 로그 캐싱 대시보드 엔드포인트에서, 데이터베이스의 I/O 병목을 완벽히 방어하고 끊김 없는 실시간 무한 스크롤 UX를 구현하기 위해 **복합 키 기반의 커서 페이징(No-offset) 기술**을 표준 정책으로 채택하여 설계하였다.
