
## 왜 필요한가?

- 서버나 클라이언트 앞에 또 다른 서버를 둠으로써 대상의 정보를 감출 수 있다.
- 캐싱을 통해 속도를 높일 수 있다.
- 네트워크에 대한 검사를 하여 보안성 증가
- 트래픽이 분산된다.

## 정의

보통 프록시(Forward Proxy)는 다음과 같다.

- 누구를 대변하는가? -> 클라이언트
- 어디에 위치하는가? -> 클라이언트와 서버 사이
- 무슨 역할을 하는가? -> 서버에 접근할 때 중간에서 요청을 대신 보내준다,
- 역할에 대한 목적
- 클라이언트 IP 숨기기
- 특정 사이트 차단
- 자주 방문하는 사이트 캐싱

리버스 프록시(Reverse Proxy)는 다음과 같다.

```
- 누구를 대변하는가? -> 서버
- 어디에 위치하는가? -> 서버와 클라이언트 사이
- 무슨 역할을 하는가? -> 클라이언트는 리버스 프록시를 서버로 알고 요청을 보내고 리버스 프록시는 요청을 받아 진짜 서버에 전달한다.
- 역할에 대한 목적
- 진짜 서버들의 IP와 구조 숨기기
- 여러 대의 서버로 요청을 나눠 보내기(로드 밸런서)
- HTTPS 암호화 처리 대행
```

# 필요한 것

- 서버 엔진
	- 보통 리버스는 Nginx, Apache 등과 같은 서버 엔진이 필요하고,
	- 포워드는 vite, react의 설정 파일을 통해 설정 할 수 있다.
- 서버 엔진에 맞는 설정
- 프록시에 연결된 네트워크 주소들


## 동작 과정

*“도메인 주소와 포트를 가지고 물리적으로 켜야하는 또 다른 서버다.”*


즉, 전통적인 동적 웹 프로그래밍에서 다음과 같은 구조를 가지고 있을 때
```
client <-> Nginx <-> Uvicorn <-> MySQL
```
이때, 포워드, 리버스 프록시를 사용하면 다음과 같은 구조를 가진다.

```
client <-> 포워드 프록시 <-> 리버스 프록시 <-> Nginx <-> Uvicorn <-> MySQL
```
포워드, 리버스 프록시를 킨다면 총 6개, 혹은 그 이상의 서버 프로그램이 작동한다는 것이다.


## 그러면 프록시 서버는 어떻게 만들까?

## 포워드 프록시
- vite를 사용해서 react를 작성하는 경우 단순하게 vite 설정을 통해 proxy를 설정하면 된다.

*”중요한건 vite는 프록시 서버와 클라이언트의 역할을 하나의 프로그램에서 포트 하나를 공유하면서 동시에 처리하는 구조라는 것이다.“*

- 혹시나 하나의 포트에서 프록시를 켰다고 될까 걱정했지만, FastAPI 관점에서는 클라이언트의 진짜 IP 주소가 가려진다.

## 리버스 프록시
- Uvicorn 자체로 프록시를 설정할 수 없고, 반드시 앞 단에 웹 서버가 필요하다.
- Uvicorn 목적 자체가 ASGI를 초고속으로 구동하기 위해 존재한다.

## 그렇다면 Axios도 프록시인가?

아니다. Axios는 프록시가 아닌 HTTP 클라이언트 라이브러리다.

프록시와 비교해보자면 다음과 같다.

- axios: 요청을 생성하고 발송하는 도구(라이브러리)
- 프록시: 요청을 대신 받는 서버 프로그램


## 프로젝트에서는 어디에서 사용하는가?

- 현재 포워드 프록시는 react에서 사용하고 있고, 리버스 프록시는 로컬로 개발하기 때문에 없다.
