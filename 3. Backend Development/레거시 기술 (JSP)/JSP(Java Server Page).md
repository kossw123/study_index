## 왜 필요할까?

- **레거시 자바 시스템의 유지보수:** 과거 웹 아키텍처의 중심이었던 서블릿(Servlet) 기술을 단독으로 사용할 때 발생하는 화면 렌더링 코드의 복잡성을 획기적으로 줄여준다.
- **MVC 패턴 구조화:** 비즈니스 로직(Controller/Model)과 화면 인터페이스(View)를 분리하는 초기 자바 웹 아키텍처(MVC Pattern) 구현의 핵심 뷰(View) 템플릿 엔진으로 기여했다.

## 정의

- **JSP (JavaServer Pages)**는 HTML 문서 내부에 자바(Java) 코드를 삽입하여 웹 서버에서 동적으로 웹 페이지를 생성한 후 클라이언트에게 응답하는 **서버 측 스크립트 언어이자 뷰 템플릿 기술**이다.

### 💡 서블릿(Servlet)과의 올바른 기술적 비교 및 발전사
- **서블릿 (Servlet)의 본질:** "자바 코드 안에 HTML을 넣는 방식"이 아니다. 서블릿은 **자바를 기반으로 웹 요청(HTTP)을 받아 동적으로 콘텐츠를 처리하는 기술 표준 명세(Specification)**이다. 다만, 과거에 서블릿으로 화면을 그리다 보니 자바 코드 내부에서 문자열로 HTML 코드를 일일이 출력(`out.println`)해야 해서 유지보수 생산성이 최악이었다.
- **JSP의 보완:** 이를 해결하기 위해 **"HTML 문서 구조를 기본 뼈대로 삼고, 필요한 동적 데이터 영역에만 자바 코드를 주입하자"**는 패러다임으로 탄생했다.
- **현실적 한계와 진화:** 그러나 JSP 내에 자바 스크립틀릿(`<% %>`) 코드가 무분별하게 섞이면서 디자이너와의 협업이 여전히 어려웠다. 이를 해결하기 위해 자바 코드를 HTML 태그 형태로 대체하는 **JSTL(JavaServer Pages Standard Tag Library)**과 **EL(Expression Language)** 기술이 결합하며 발전했다.

## 동작 과정 및 라이프사이클 (Lifecycle)

JSP 파일은 브라우저가 직접 해석할 수 없다. 내부적으로 **서블릿(Servlet) 클래스로 변환되어 구동**되는 철저한 백엔드 기술이다.

```
[클라이언트 요청] ➔ http://server/index.jsp  
│  
▼  
[웹 서버 (Nginx 등)] ➔ WAS(Tomcat) 내부의 JSP 엔진(Jasper)으로 토스  
│  
├─> 1. Translation: `.jsp` 파일을 `.java` 서블릿 소스코드로 변환  
├─> 2. Compilation: `.java` 코드를 `.class` 서블릿 클래스로 컴파일  
│  
▼  
[서블릿 컨테이너 메모리 적재] ➔ 서블릿 객체가 실행되며 최종 HTML 텍스트를 '직접 생성'  
│  
▼  
[최종 HTML 스트림 반환] ➔ 완성된 HTML 텍스트를 웹 서버를 거쳐 브라우저에 그대로 바이패스 전달
```

1. **JSP 페이지 요청:** 클라이언트(웹 브라우저)가 특정 JSP 페이지를 요청하면 웹 서버가 이를 받아 WAS(서블릿 컨테이너)의 JSP 엔진(Jasper)으로 전달한다. 
2. **자바 소스 변환 (Translation):** JSP 엔진이 `.jsp` 파일을 해석하여 표준 서블릿 규격에 맞는 자바 소스코드(`.java`) 파일로 변환한다. 
3. **컴파일 (Compilation):** 변환된 `.java` 파일을 JVM이 실행할 수 있는 바이트코드인 서블릿 클래스(`.class`) 파일로 컴파일한다. 
4. **실행 및 결과 응답:** 컴파일 완료된 서블릿 클래스가 메모리에 로드되어 요청을 처리하며, **출력 스트림을 통해 브라우저가 읽을 수 있는 완성형 HTML 텍스트 데이터를 직접 생성**하여 웹 서버를 거쳐 클라이언트에게 전송한다. 

> ⚠️ **[실무 핵심] 프로덕션 환경에서의 사전 컴파일 (Pre-compilation)** 
> > 기본적으로 JSP는 런타임에 첫 요청이 들어올 때 변환 및 컴파일을 수행하므로 첫 방문자는 느린 응답(Cold Start)을 겪는다. 이를 방지하기 위해, 실무 및 엔터프라이즈 운영 환경에서는 빌드/배포 단계에서 Gradle 이나 Maven 플러그인을 활용하여 **모든 JSP를 미리 `.class` 서블릿 파일로 컴파일(사전 컴파일)하여 패키징**하는 전략을 채택한다. 
## 프로젝트에서는 어디에서 사용하는가? 
- **현대적 아키텍처와의 전환:** 
	- 현재 우리 프로젝트는 백엔드와 프론트엔드가 완벽히 분리된 분산 아키텍처 환경(FastAPI + React) 또는 현대적인 컴포넌트 아키텍처를 지향하므로, 서버 사이드 렌더링(SSR)의 레거시 기술인 JSP는 사용하지 않는다. 
- -**지식의 가치:** 
	- 그러나 웹의 동적 제어 흐름과 서버 측 템플릿 렌더링의 원천 기술인 서블릿/JSP 라이프사이클을 이해함으로써 웹 아키텍처의 변천사와 백엔드 엔진의 구조를 깊이 있게 파악하는 자산으로 삼는다.
