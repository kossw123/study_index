## 왜 필요한가?

- [시스템의 크기에 따른 서버 분리 기법의 발전]
	- [문제점:]
		- 초기에는 하나의 서버에서 모두 실행되는 모놀리식(Monolithic)이였다.
	- [해결책:]
		- 기술의 발전에 따라 각 기능(도메인)별로 각 서버를 둬서 하나의 기능이 멈춰도 다른 기능이 살아있는 방식을 작성할 수 있게 되었다.
- [기능마다 분리된 서버를 사용해 생기는 문제]
	- [문제점:]
		- 기능마다 분리된 서버끼리 통신을 해야한다.
	- [해결책:]
		- RPC는 분리된 서버끼리의 통신을 추상화한다.

## 정의

> 다른 컴퓨터에서 있는 함수를, 마치 내 프로그램 안에 있는 함수처럼 호출하는 방식이다.

- 모놀리식 구조의 프로그램에서는 내부의 함수를 호출하기만 하면 그만이였다.
- 그러나 기능 별로 분리된 서버에 있는 기능을 실행하려면 다음과 같은 그림이 그려진다.
```
Order Server
     |
     | "결제 승인해줘"
     ↓
Payment Server
```

## 동작 과정

```
① 함수 호출
      ↓
② 요청 변환(직렬화)
      ↓
③ 네트워크 전송
      ↓
④ 원격 함수 실행
      ↓
⑤ 결과 변환 후 반환
```

## 동작 과정 예시

- 아래와 같으 별도의 서버를 현재 서버에서 불러온다고 한다면,
```
result = payment.confirm(
    order_id="123",
    amount=10000
)
```
- 대략 다음과 같이 내부적으로 움직인다.
```
Client
 │
 │ confirm(order_id=123, amount=10000)
 ↓
RPC Client Stub(*)
 │
 │ Serialize
 ↓
Network
 │
 ↓
RPC Server
 │
 │ confirm() 실행
 ↓
Payment Service
 │
 ↓
결과
 │
 │ Serialize
 ↓
Network
 │
 ↓
RPC Client
 │
 ↓
result
```
## RPC와 HTTP API의 차이

|       | REST API             | RPC                |
| ----- | -------------------- | ------------------ |
| 관점    | 리소스 중심               | 함수 / 행위 중심         |
| 예     | `POST /payments`     | `ConfirmPayment()` |
| 생각 방식 | "Payment 리소스를 생성한다." | "결제를 승인한다."        |
| 인터페이스 | HTTP + URL           | 함수 / 메서드           |
| 대표 기술 | REST                 | gRPC               |
| 장점    | 웹과 잘 맞음              | 서비스 간 호출에 자연스러움    |
## 실무에서의 사용 방법

> MSA 구조의 통신에서 RPC를 많이 사용한다.

- 다음과 같은 MSA 구조의 대형 쇼핑몰의 사이트에서 주문을 생성한다고 가정해보자.

```
                 API Gateway
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
   Order Service  User Service  Product Service
       │
       │ RPC
       ↓
   Payment Service
       │
       │ RPC
       ↓
   Reward Service
```

- Order 도메인의 Application Layer에서는 다음과 같이 다른 도메인의 서버에 접속하여 다음과 같이 기능을 호출할 수 있다.
```
Order Service
     │
     ├── UserService.GetUser()
     │
     ├── ProductService.CheckStock()
     │
     ├── PaymentService.Authorize()
     │
     └── RewardService.AddPoint()
```

## 장점

1. [개발자가 함수 호출처럼 생각할 수 있다.]
	- 직관적으로 다음과 같이 호출된다.
		- `payment.confirm()`
2. [서비스 간 계약을 명확하게 만들 수 있다.]
	- RPC의 대표적인 gRPC에서는 Protocol Buffers를 사용해, 계약을 명확히 정의할 수 있다.
	- 그래서, **[해당 서비스가 어떤 데이터를 받고, 무엇을 반환하는가?]** 가 명확하다.
3. [서비스 간 통신에 적합하다.]
	- `브라우저 <-> 서버`간 통신 보다는 `서버 <-> 서버`간 통신에 어울린다.
4. [성능을 중요하게 볼 수 있다.]
	- 특히 gRPC는 HTTP/2와 Protocol Buffer를 사용해서, 서비스 간 통신을 효율적으로 만들 수 있다.

## 단점

1. [함수처럼 보여도 어찌됐든 네트워크 호출이다.]
	- 함수와 비슷하게 생겼어도, 실제로는 네트워크 호출이다.
	- 네트워크 호출은 언제든 실패한다.
2. [멱등성 문제]
	- 호출을 하고, 결과까지 성공했지만, 응답을 못받는 경우가 발생한다.
3. [RPC 지옥]
	- 서비스를 너무 잘게 쪼개면, 기능 하나를 처리하기 위해 RPC가 여러번 발생한다.
	- 그러면 한 서비스가 느려지는 순간 전체 기능이 느려질 수 있다.

## RPC를 사용하는 기준

- [RPC가 적합한 경우]
	- **"지금 결과가 필요할 때"**
- [이벤트가 적합한 경우]
	- **"이 일이 발생했다는 사실만 알려주면 될 때"**

> RPC는 행동을 요청할 때 사용하고,
> Event는 사실을 전달할 때 사용한다.
