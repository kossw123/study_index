## 왜 필요할까?

- **분산 시스템의 복잡성 추상화:** 모놀리식 아키텍처에서는 내부 함수 호출만으로 모든 비즈니스 로직을 처리할 수 있었다. 하지만 시스템의 규모가 커져 마이크로서비스 아키텍처(MSA)로 서버를 도메인별로 분리하게 되면서, 서로 다른 서버에 존재하는 기능을 실행하기 위한 네트워크 통신 파이프라인이 필요해졌다.
- **로컬 함수 수준의 개발 경험:** RPC는 네트워크 통신(소켓 연결, 직렬화, 데이터 전송 등)의 하위 레이어 복잡성을 내부적으로 숨겨준다. 덕분에 개발자는 **원격 서버에 있는 기능을 마치 현재 프로그램 내부의 로컬 함수를 호출하는 것처럼 직관적으로 개발**할 수 있다.

## 정의

- **RPC (Remote Procedure Call, 원격 프로시저 호출)**는 네트워크로 연결된 다른 컴퓨터(서버)의 함수나 프로시저를, 호출하는 측의 로컬 제어 흐름 내에서 직접 실행할 수 있게 해주는 **네트워크 통신 아키텍처 스타일**이다.

---

## 동작 과정 (Stub 아키텍처 구조)

```
[Client App] ──① 함수 호출 ──> [Client Stub] ──② 직렬화(Serialization) ──┐  
																	   │ (Network) 
[Server App] <──④ 함수 실행 ── [Server Stub] <──③ 역직렬화(Deserialization) ┘
```

- **클라이언트 스텁 (Client Stub):** 개발자가 호출한 함수 매개변수를 네트워크로 전송 가능한 바이트 형태의 데이터로 변환(직렬화/Marshalling)하고, 원격 서버로부터 받은 응답을 다시 역직렬화하여 앱에 반환한다. 
- **서버 스텁 (Server Stub):** 네트워크 요청을 받아 역직렬화한 뒤, 서버 내부의 실제 비즈니스 로직(함수)을 호출하고 그 결과값을 다시 직렬화하여 클라이언트에게 송신한다.

## 패러다임 비교: REST 아키텍처 vs RPC 아키텍처 

> ⚠️ **[주의] RPC는 HTTP와 배타적인 개념이 아니다.** RPC는 아키텍처 스타일이며, 현대 RPC의 대표 주자인 **gRPC는 전송 프로토콜로 `HTTP/2`를 백엔드에서 전면 채택**하여 사용한다. 따라서 본 비교는 네트워크 프로토콜이 아닌 **'설계 관점'**의 차이이다. 

| 비교 항목        | REST 아키텍처 스타일                      | RPC 아키텍처 스타일 (gRPC 등)                        |
| ------------ | ---------------------------------- | -------------------------------------------- |
| **핵심 관점**    | **리소스 (Resource) 중심**              | **함수 및 행위 (Procedure) 중심**                   |
| **인터페이스 형태** | 명사형 표준 HTTP 메서드 + URL 경로           | 명확한 스펙 정의서 기반의 원격 함수/메서드                     |
| **호출 예시**    | `POST /v1/payments`                | `ConfirmPayment(order_id, amount)`           |
| **설계 사고 방식** | "결제라는 '자원(Resource)'을 서버에 생성한다."   | "결제를 승인하는 '행위(Action)'를 원격 유스케이스로 실행한다."     |
| **주요 장점**    | 웹 표준에 완벽히 부합하며, 범용적인 클라이언트 대응이 쉽다. | 서비스 간(서버 대 서버) 계약이 명확하며, 유스케이스 흐름 처리가 자연스럽다. |

## 장점 및 단점 
### 1. 장점 
- **강력한 타입 안전성과 명세화:** gRPC 등 현대 RPC 기술은 Protocol Buffers 같은 IDL(인터페이스 정의 언어)을 사용해 통신 규격을 강제한다. **어떤 데이터를 받고 무엇을 반환하는지 컴파일 시점에 명확히 검증**되므로, 서버 간 인터페이스 계약(Contract)이 깨질 위험이 없다. 
- **성능 최적화:** 특히 gRPC는 `HTTP/2` 아키텍처의 멀티플렉싱과 이진 바이너리 프로토콜 스펙을 극대화하여 활용하므로, 텍스트 기반의 전통적인 REST API 통신 대비 데이터 크기가 작고 처리 처리 속도가 압도적으로 빠르다. 
### 2. 단점 및 실무 주의점 
- **네트워크 한계의 착시:** 
	- 코드상으로는 단순한 로컬 함수처럼 보이지만, **본질은 언제든 실패할 수 있는 네트워크 통신(I/O)**이다. 타임아웃, 망 유실, 일시적 단절에 대비한 재시도(Retry) 및 서킷 브레이커 전략이 설계에 반드시 수반되어야 한다. 
- **분산 환경의 멱등성 문제:** 
	- 요청은 성공했으나 응답을 받는 과정에서 네트워크가 단절되면, 클라이언트는 실패로 인지하고 재요청을 날려 **중복 처리 사고**가 날 수 있다. 따라서 핵심 원격 함수는 반드시 **멱등성(Idempotency)**을 보장하도록 설계해야 한다. - **분산 서비스 간 타이트한 결합(RPC 지옥):** 비즈니스 로직 하나를 처리하기 위해 수많은 서버에 동기식 RPC 호출을 연쇄적으로 수행하면, 단 하나의 하위 서버만 느려져도 전체 시스템의 응답 속도가 무너지는 장애 전파 현상이 발생한다.

## 🏗️ 설계 가이드라인: RPC vs 이벤트 기반 통신(EDA) 

시스템 구조를 짤 때 RPC와 이벤트를 분기하는 일반적인 **설계 판단의 기준 예시**는 다음과 같다. (※ 기술적 제약이 아닌 아키텍처 아웃라인이다.) 

- **RPC 아키텍처 도입이 유리한 경우 (행위의 요청):** 
	- 서비스 간 상호작용 과정에서 **즉각적인 결과 데이터 확인이나 정합성 검증이 설계상 반드시 필요한 구조**일 때 유용하다. (단, 필요에 따라 결과를 대기하지 않는 **비동기 RPC 호출** 형태로도 유연하게 응답 루틴을 설계할 수 있다.) 
	- *예: "주문 서비스가 상품 서비스에 호출을 던져 현재 재고가 진짜 남아있는지 확인하고 차감 처리를 완료 받아야 하는 경우"* 
- **이벤트 기반 아키텍처(EDA) 도입이 유리한 경우 (사실의 전달):** 
	- 특정 비즈니스 사건이 **"발생했다는 사실"**만 주변 시스템에 전파하면 되고, 주 시스템이 그 이후의 연쇄 작업 성공 여부를 굳이 붙잡고 기다릴 필요가 없는 느슨한 결합 구조에 적합하다. 
	- *예: "주문 및 결제가 완전히 완료되었으니, 메일 발송 시스템과 통계 시스템은 알아서 이 사건을 전송받아 각자 작업을 처리하라고 이벤트를 발행하는 경우"*
