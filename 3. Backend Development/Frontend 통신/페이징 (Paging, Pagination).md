## 왜 필요한가?

- **[1. 서비스 성능 및 속도 개선]
	- [1. DB 개선]
		- DB가 대량의 데이터를 한 번에 조회하고 정렬하면 엄청난 메모리를 소모하기에, 여러 페이지에 걸쳐서 나눠 보여주면 이를 개선할 수 있다.
	- [2. 네트워크 과부하]
		- 수백 MB에 달하는 대용량 데이터가 네트워크를 통해 전송될 때, 사용자의 데이터 요금을 절약하고, 전송 속도를 대폭 늘릴 수 있다.
	- [3. 브라우저 다운]
		- 스마트폰이나, PC의 브라우저가 대용량의 데이터를 한번에 보여주면 메모리 부족으로 렌더링이 멈출 수 있기에, 이를 해결할 수 있다.
- **[2. 비용 절감]**
	- [1. 서버 비용 아끼기]
		- 대용량 데이터를 한 번에 가져와봤자, 볼 수 있는건 한계가 있다.
		- 보지 않을 데이터를 가져오는 것보다 볼 수 있는 데이터만 가져오는게 비용을 아낄 수 있다.
- **[3. 사용자 경험(UX) 향상**
	- [1. 빠른 첫 화면]
	- [2. 원하는 정보 탐색]

## 정의

- 대량의 데이터를 일정 크기로 나눠 여러 페이지에 걸쳐 보여주는 기술이다.
	- e.g) 1페이지, 2페이지, ...


> 즉, 필요한 만큼만 조금씩 나눠 가져와, 시스템을 안전하게 만들고 사용자를 기다리지 않게 하는 기술이다.

## 종류

### 오프셋 기반 (Offset-based)

- DB의 `LIMIT`와 `OFFSET` 쿼리를 사용해, 특정 위치부터 원하는 갯수만큼 데이터를 가져오는 방식이다.
- [단점]
	- 뒤 페이지로 갈수록 DB가 앞의 데이터를 **모두 읽고 건너뛰어야 해서, 속도가 느리다.**
	- 데이터가 추가/삭제되면 중복이 발생하거나 누락될 수 있다.
		- e.g) [<] [1] [2] [3] [>]

### 커서 기반 (Cursor-based / No-offset)

- 페이지 번호 대신 **"마지막으로 본 아이템의 ID 또는 정렬 기준 값"** 을 커서로 두고, 커서 이후의 데이터를 가져오는 방식이다.
- [장점]
	- 대용량 데이터를 가져와도 성능이 일정하게 빠르며, 실시간으로 추가되어도 페이지 밀림 현상이 없다.
		- 인스타그램, 유튜브의 무한 스크롤, 더보기 버튼


## 처리 과정

- **[1. 클라이언트의 요청]**
	- 쿼리 스트링을 사용해, 서버에게 요청할 페이지 정보를 보낸다.
		- e.g) : `/api/posts?page=2&size=10`
- **[2. 서버 SQL 계산]**
	- 서버는 클라이언트가 보낸 값을 바탕으로 DB 조회 쿼리를 작성한다.
		- `ref) 오프셋 계산 공식: OFFSET = (Page - 1) * size`
		- `2페이지라면 앞의 10개를 건너뛰고 11번째부터 조회`
- **[3. DB 데이터 추출]**
	- DB에서 조건에 해당하는 데이터와, 전체 데이터 갯수를 함께 조회한다.
- **[4. 서버 응답]**
	- 서버는 조회한 데이터를 프론트엔드에게 JSON형태로 전송
- **[5. 화면 렌더링]**
	- 브라우저는 받은 데이터를 화면에 렌더링
