## 왜 필요한가?

- 커밋 히스토리를 깔끔한 한 줄로 정렬하기 위해 필요하다.
- `git merge`를 사용하면 수많은 머지 커밋과 복잡한 브랜치 떄문에 히스토리를 파악하기 어렵기 때문에 rebase가 필요하다.
	- 시작점 재설정
	- 커밋 재적용
	- 히스토리 선형화


### Merge vs Rebase

- 다음과 같은 상황을 가정한다.

```
      D -- E (feature)
     /
A -- B -- C (main)
```

1) `git merge`를 사용할 경우

```
      D ---- E (feature)
     /        \
A -- B -- C -- F (main)
```

2) `git rebase`를 사용할 경우

```
A -- B -- C (main) -- D` -- E` -- F (feature)
```

## 정의

- 브랜치의 공통 조상(base)를 다른 최신 커밋으로 변경하여, 커밋 히스토리를 재작성하는 명령어다.
- 쉽게 말해, 브랜치의 시작 뿌리를 최신 상태의 다른 브랜치 뒤로 "옮겨 심는 기능"이다.
- 기존 커밋의 변경 사항을 복사해, "완전히 새로운 커밋"을 만들어 내는 파괴적인 작업이다.

## 동작 과정

```
$ git switch feature // 1. 작업 브랜치로 이동
$ git rebase main // 2. main 브랜치의 최신 커밋 뒤로 feature의 뿌리(Base)를 이동
```


### Interactive rebase

- 지저분한 커밋들을 하나로 깔끔하게 묶거나 지우는 방법이다.
- 원격 저장소에 push된 커밋에는 절대로 git rebase를 쓰면 안된다.
	- 커밋 ID를 새롭게 바꾸기 때문에, 다른 사람의 원격 저장소 이력이 꼬일 수 있다.

1) interactive rebase 입력 

```
$ git rebase -i HEAD~3 // head 포인터로부터 3번쨰 커밋까지 rebase
```

2) 텍스트 편집기가 열리면서 커밋 목록 나오는데, 커밋 해시 앞 단어(pick)를 수정하여 원하는 작업으로 변경

	- pick : 커밋을 그대로 유지
	- squash : 이전 커밋과 합치기 (커밋 메시지도 합친다)
	- drop : 해당 커밋을 삭제하고 변경사항 폐기

```
pick a1b2c3d 첫 번째 기능 구현
squash e5f6g7h 오타 수정       <-- pick을 squash로 변경
squash i9j0k1l 진짜 최종 수정  <-- pick을 squash로 변경
```
## 관련 개념

#VCS, #git 













"rebase는 기존 commit의 변경사항(diff)를 추출해, 새로운 base commit 위에 다시 적용하여 parent가 변경된 새로운 commit을 생성한다.“

rebase는 commit의 base를 변경한다.

여기서 base는 commit의 부모를 의미한다.

즉,

```
A ─ B ─ C (main)
     \
      D ─ E (feature)
```


D의 parent는 B이고, E의 parent는 D이다.

그리고 rebase를 다음과 같이 실행한다.

```
git checkout feature
git rebase main
```

그러면 다음과 같이 변경된다.

```
A ─ B ─ C (main)
        \
         D' ─ E' (feature)
```

이런식으로 commit의 base를 변경하는 행위를

rebase 명령어를 통해 실행할 수 있다.

commit graph의 관점에서는 다음과 같은 구조가

```
A ─ B ─ C
     \
      D ─ E
```

다음과 같이 변경된다.

```
A ─ B ─ C ─ D' ─ E'
```

# 왜 기존 commit을 새로운 commit에 적용하는데, 새로 생성하기까지 할까?

알아둬야 하는게, rebase를 하면 commit이 이동하는게 아닌, 기존 commit에서 diff를 추출한 뒤, diff를 새로운 위치에 적용해서, 새로운 commit을 생성하는 것이다.

즉,

1. 기존 commit에서 diff(변경사항) 추출

2. 새로운 base commit, 즉 rebase 후에 새로 생성되는 commit들의 parent가 되는 commit의 위에서 diff를 적용한다. 굳이 이렇게 표현하는 이유는 rebase는 브랜치 자체가 아닌 commit 위에서 동작하기 때문이다.

3. diff가 적용된 새로운 commit을 생성

# merge와의 차이점

merge는 서로 다른 브랜치의 최신 commit을 부모로 가지는 새로운 merge commit을 생성하고 브랜치를 통합한다.

이때 history는 보존된다.

그러나 rebase는 서로 다른 브랜치에서 특정 commit의 base를 변경함으로써 history가 변경된다.

그러나 rebase는 특정 브랜치의 commit들을 다른 commit(또는 다른 브랜치의 commit)위에 다시 적용하여, parent를 변경하고 새로운 commit을 생성한다.

이때 history는 재작성된다.

- history가 유지 혹은 재작성된다는 것은 commit ID가 유지되거나 바뀌는 것을 의미한다.
    

# Squash

짓누르다라는 의미를 가진 Squash는 여러 commit을 합쳐 하나의 commit으로 만들 수 있다.

```
$ git rebase -i <병합을 시작할 commit tag>
```

위 명령어를 실행하면 pick, squash할 창이 나온다.

- 이때 주의할 점은 맨 위에 commit은 pick으로 남겨둬야 한다.
    
- 왜냐하면 맨 위 commit을 기준으로 parent를 변경하기 때문이다.
    

합칠 commit들은 모두 squash로 변경 후 저장하면 수정할 commit message를 작성하는 창이 나온다.

- 맨 처음부터 하려면 다음과 같은 명령어를 사용하면 된다.
```
$ git rebase -i --root
```
