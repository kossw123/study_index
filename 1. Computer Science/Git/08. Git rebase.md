## 왜 필요한가?

- 커밋 히스토리를 깔끔한 한 줄로 정렬하기 위해 필요하다.
- `git merge`를 사용하면 수많은 머지 커밋과 복잡한 브랜치 떄문에 히스토리를 파악하기 어렵기 때문에 rebase가 필요하다.
	- 시작점 재설정
	- 커밋 재적용
	- 히스토리 선형화


### Merge vs Rebase

- 다음과 같은 상황을 가정한다.

```
      D -- E (feature)
     /
A -- B -- C (main)
```

1) `git merge`를 사용할 경우

```
      D ---- E (feature)
     /        \
A -- B -- C -- F (main)
```

2) `git rebase`를 사용할 경우

```
A -- B -- C (main) -- D` -- E` (feature)
```

## 정의

- 브랜치의 공통 조상(base)를 다른 최신 커밋으로 변경하여, 커밋 히스토리를 재작성하는 명령어다.
- 쉽게 말해, 브랜치의 시작 뿌리를 최신 상태의 다른 브랜치 뒤로 "옮겨 심는 기능"이다.
- 기존 커밋의 변경 사항을 복사해, "완전히 새로운 커밋"을 만들어 내는 파괴적인 작업이다.

## 동작 과정

```
$ git switch feature // 1. 작업 브랜치로 이동
$ git rebase main // 2. main 브랜치의 최신 커밋 뒤로 feature의 뿌리(Base)를 이동
```


### Interactive rebase

- 지저분한 커밋들을 하나로 깔끔하게 묶거나 지우는 방법이다.
- 원격 저장소에 push된 커밋에는 절대로 git rebase를 쓰면 안된다.
	- 커밋 ID를 새롭게 바꾸기 때문에, 다른 사람의 원격 저장소 이력이 꼬일 수 있다.

1) interactive rebase 입력 

```
$ git rebase -i HEAD~3 // head 포인터로부터 3번쨰 커밋까지 rebase
```

2) 텍스트 편집기가 열리면서 커밋 목록 나오는데, 커밋 해시 앞 단어(pick)를 수정하여 원하는 작업으로 변경

	- pick : 커밋을 그대로 유지
	- squash : 이전 커밋과 합치기 (커밋 메시지도 합친다)
	- drop : 해당 커밋을 삭제하고 변경사항 폐기

```
pick a1b2c3d 첫 번째 기능 구현
squash e5f6g7h 오타 수정       <-- pick을 squash로 변경
squash i9j0k1l 진짜 최종 수정  <-- pick을 squash로 변경
```
